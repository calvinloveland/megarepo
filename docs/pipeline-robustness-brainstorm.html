🔧 NixOS Pipeline Robustness — Brainstorm

Ideas to prevent another thinker-like outage.
Based on: SSH-triggered rebuild timed out, machine went offline, no remote recovery path.

📡 Deployment resilience

easy Use nixos-rebuild boot instead of switch

switch activates the new config immediately. If the activation breaks networking, you lose your SSH session mid-flight. boot only installs the new config to the bootloader entry — the next cold boot uses it, but the current session stays untouched.
Change: Remote deploys default to nix build .#host + nixos-rebuild boot instead of nixos-rebuild switch. A Warden check on the next boot confirms success. For switch, only use it when you have console/out-of-band access.

medium Keep the SSH session alive during long rebuilds

The rebuild timed out after 10 minutes. SSH dropped, and the activation was left partially complete. If the session had stayed alive, it would have finished the switch safely.
Options:
a) Use tmux or screen on the remote host — detach before the rebuild, re-attach after to check status. This survives SSH drops.
b) Use nix copy to send the built derivation to the remote, then run the activation script locally as a Warden auto-remediation step — no long-lived SSH needed.
c) Warden deploys: the remote Warden agent pulls the new config and activates it locally, never relying on an SSH session staying open.

medium Pre-flight validation before remote deploy

The new hardware-configuration.nix was generated remotely via sysfs probes. It might have had an incorrect boot partition definition. No dry-run was performed.
Change: Before any remote nixos-rebuild switch, run: 
nix build .#host.config.system.build.toplevel          # build locally first
nix copy --to ssh://remote-host .#host                 # push the derivation
ssh remote "nix-store --realise /nix/store/...-system" # verify it's valid
If any step fails, don't proceed. Also consider running nix eval to check key options on the remote before deploying.

🔁 Self-healing and rollback

easy Warden rollback remediation

After a rebuild, the Warden's system-config check detects when the config is stale (hasn't been rebuilt in N days). But there's no check for the inverse: a bad deployment.
Change: Add a health-after-rebuild check that runs 5 minutes after a rebuild and verifies:
  • SSH is still reachable
  • Tailscale is connected
  • Key services are running
  • All Warden checks pass
If the check fails, auto-trigger nixos-rebuild switch --rollback.

medium Atomic deployment via boot entries

NixOS already supports boot entries (generations). The current generation is always safe. The failure scenario is: new generation is activated, it breaks networking, you're locked out.
Change: Use a "two-stage activate" pattern:
  1. nixos-rebuild boot — sets the new config as default for next boot, but doesn't activate it now
  2. Reboot the machine (or let the Warden do it at 3am)
  3. If the machine doesn't check in via Tailscale within 10 minutes, the bootloader auto-selects the previous generation (set boot.loader.grub.fallbackBoot)
This is similar to how firmware updates work on routers (dual-image + watchdog).

hard Watchdog-triggered rollback

If the machine locks up during activation, nobody can SSH in to fix it. A hardware watchdog can auto-reboot after a timeout.
Change: Enable the NixOS hardware watchdog: 
boot.kernelParams = [ "watchdog_thresh=60" ];
hardwarewatchdog.enable = true;
If the system hangs during activation, the watchdog triggers a reboot after 60 seconds. On reboot, NixOS's bootloader can fall back to the previous generation if the new one fails to boot (GRUB has boot.loader.grub.fallbackBoot). systemd-boot also has a similar mechanism with boot.loader.systemd-boot.default.

🔐 Infrastructure hardening

easy Out-of-band access via Tailscale SSH

Tailscale has a built-in SSH server that's separate from the system SSH daemon. It keeps running even if OpenSSH is reconfigured or down.
Change: Enable Tailscale SSH on all hosts: 
services.tailscale.enable = true;
services.tailscale.extraUpFlags = [ "--ssh" ];
This gives a fallback SSH path if nixos-rebuild switch breaks OpenSSH config. Haswell already has Tailscale — just needs --ssh flag.

easy Standardize sudo passwords across hosts

Three different passwords on three hosts (haswell=12345, thinker=Tiber1909!, 1337book=TemporaryPassword1776!). During an incident, you don't want to guess which password works where.
Status: Already done — the warden user has NOPASSWD: ALL. The problem was deploying via calvin (who needs a password). The fix is to use the Warden's existing passwordless sudo by having Wardens self-deploy.

medium Warden-to-Warden deployment pipeline

Currently, the deploy process is: build on haswell → SSH into host as calvin → type password → run nixos-rebuild. The Warden warden user already has passwordless sudo (NOPASSWD: ALL at warden.nix:258), but the deploy path doesn't use it. If SSH fails mid-deploy, the host is stranded.
Change: Let the remote Warden agents pull and deploy their own configs:
  1. haswell builds all three configurations
  2. haswell pushes the built derivations to peer Wardens via nix copy --to
  3. The peer Warden runs sudo nixos-rebuild switch locally (passwordless, as warden)
  4. If activation fails, the peer Warden auto-rolls back
No SSH-as-calvin session needed — the activation runs on the target host as warden directly.

medium Deploy script with pre-flight + timeout + fallback

The ad-hoc ssh host 'echo password | sudo nixos-rebuild switch' pattern is fragile. A deploy script should handle all edge cases.
Script: pi-deploy.sh that:
  1. Builds the config locally first
  2. Runs pre-flight checks (eval, dry-build)
  3. Copies the derivation to the target via nix copy
  4. Activates via SSH with tmux (so it survives disconnection)
  5. Waits for the target to check back in via Tailscale/Warden heartbeat
  6. If no heartbeat within N minutes, auto-triggers rollback via Warden peer API
