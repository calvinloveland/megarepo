k33p — typed version control for the real shape of a project

One URL. Four content kinds. A role for whoever's looking.

Status: design draft · v0.1 · lives at ideas/k33p/design.html

Thesis. A modern project is not a git repository with some bag of side channels bolted on. It is a typed collection of content channels — public source, private source, third-party dependencies, and built artifacts — each with its own transport, its own access rules, and its own definition of "history." k33p makes those channels first-class, ties them together with a signed manifest, and lets a user materialize exactly the channels their role needs. Nothing more, nothing less.

🧩 The problem

An open source project has four distinct content kinds. Git handles one of them well.

Content kind Example What owns it today
src Application code, tests, docs git on github/gitlab/sourcehut
private .env, API keys, internal notes, sensitive code paths …a prayer, plus a .gitignore
deps Third-party libraries, transitive lockfile npm / cargo / pip / oci, separately
artifacts Binaries, container images, generated PDFs CI artifact store, ghcr.io, releases page

And four kinds of consumers, each of whom wants a different slice:

  • End user — wants the binary, doesn't want the source code on disk at all.
  • Developer — wants source + dependencies, doesn't want 1.2 GB of git history.
  • Maintainer — wants source + secrets + history + the ability to sign a release.
  • Auditor / supply-chain reviewer — wants signed manifests and full history, not the source tree.
The current answer is a fragile glue job: .env.example checked in, secrets stored in 1Password, a CI script that wires it all together, a separate container registry for artifacts, a separate lockfile for deps, and a strong cultural rule that nobody ever accidentally commits a credential. This is not version control. It's an honor system.

k33p's answer is to type the channels. Make each of them a first-class object with its own semantics, give the project one URL, and let each consumer declare what they need via a role.

🧱 Core abstractions

k33p has six concepts. Everything else is a combination of them.

1. Project

A name, a manifest (k33p.yaml), a set of channels, and an optional cross-channel lock (k33p.lock). The thing a person points at with one URL.

2. Channel

A typed content stream — one of source, secrets, dependencies, or artifacts. Each channel has a transport (where its bytes live), an access policy, a history policy, and a retention policy. Channels are independent: a secret channel knows nothing about a source channel, except where the manifest points them both at the same project.

3. Ref

A pointer to a specific state in a channel. For source: a commit SHA, a tag, a branch. For secrets: a content hash. For deps: a lockfile revision. For artifacts: a signed manifest ID. Refs are typed per channel because the shape of "a specific state" differs.

4. Role

A named bundle of channel subscriptions + history settings. The UX win: instead of a one-size-fits-all git clone, a user picks a role and k33p materializes only what that role needs.

5. Lock

k33p.lock pins every channel to a specific ref at a specific time. Reproducible across machines. The single file that turns a project from "I have some code and maybe some artifacts" into "I have this code and those artifacts, verifiably."

6. Materialized view

What's actually on disk for a given project + role + lock. Switching roles changes the view. A role can be re-applied at any time; k33p adds, removes, and updates channels to match.

📜 The manifest

Every project carries a k33p.yaml at its root, committed to the source channel like any other file. It declares the channels and the roles. A minimal real example:

# k33p.yaml — committed to the src channel
project: coolproject
description: A thing that does stuff

channels:
  src:
    type: source
    transport: git+https://github.com/coolproject/coolproject
    visibility: public
    history: full

  private:
    type: secrets
    transport: k33p+https://secrets.coolproject.com/coolproject
    encryption: age
    recipients: ["maintainers@coolproject.com"]
    history: none                # secrets are point-in-time

  deps:
    type: dependencies
    transport: oci+https://registry.coolproject.com/coolproject-deps
    resolver: cargo
    pinned: true
    history: lockfile

  artifacts:
    type: artifacts
    transport: oci+https://registry.coolproject.com/coolproject
    content_addressed: true
    signed: true
    history: ring(10)            # last 10 signed manifests

roles:
  end-user:    { channels: [artifacts],                history: none    }
  developer:   { channels: [src, deps],                history: shallow }
  maintainer:  { channels: [src, private, artifacts],  history: full,   publish: [src, private, artifacts] }
  ci:          { channels: [src, deps, private],       history: shallow, publish: [artifacts] }
  auditor:     { channels: [src, artifacts],           history: full,   verify: strict }

Three properties to notice:

  1. Channels are declarative. A project doesn't tell you how to fetch; it tells you what a channel is and where its bytes come from. The role tells you which channels are interesting.
  2. History is per-channel. A history: key on every channel. This is the central insight — see below.
  3. Roles are bundles, not permissions. A role says "give me src@shallow + deps." It does not say "give me write access to private." Authorization is a separate, transport-level concern.

📦 The four channels

Each channel type is a different kind of thing with different storage, transport, and rules. They're not just "labels" — they're distinct content domains with distinct semantics.

src Source

The classic version-controlled code. Backed by git; k33p is a thin wrapper, not a replacement. Visibility is public by default (matches the user's stated mental model of "an open source project"), but the visibility: private option exists for closed source.

Why git: it's not perfect, but it's universal, well understood, and battle-tested. The cost of replacing it is enormous and the win is small.

Default history: full for maintainers, shallow for developers and CI, none for end users (they don't have this channel at all).

private Secrets

Encrypted at rest, encrypted in transit, encrypted in any cache. Each blob is its own ciphertext, content-addressed, and addressed by content not by path — rotating a secret doesn't rewrite history because there is no history.

Why a separate channel: a .env file is not a "file" in the source sense. Its lifetime is "now," not "v1.0.0." Its access model is "decrypt with key X," not "clone over HTTPS." Putting it in the source channel is what causes every secret leak in the wild.

Decryption keys live in the OS keychain, on a hardware token, or behind an SSH agent. They are never committed, never on disk in plaintext, never in the source channel.

On disk: encrypted blobs in .k33p/private/; the working tree never contains plaintext. Commands that need secrets use k33p exec -- which mounts decrypted values into the subprocess environment without writing them to disk.

Default history: none. Always.

deps Dependencies

Third-party code the project depends on, pinned by content hash. A lockfile (the resolution) and a blob store (the resolved bytes), treated as one channel.

Transports: any package ecosystem is a valid transport. Cargo, npm, pip, Go modules, OCI, Nix flakes. k33p doesn't replace them; it wraps them. The transport field says "I use cargo"; k33p shells out to cargo for resolution and re-uses its lockfile as the k33p ref.

Vendoring is the default. k33p fetch deps materializes the locked set as files in .k33p/deps/ so the build is reproducible offline. A developer without internet can still build, because the deps are already on disk.

Project-specific deps (a forked internal library, a private package) live in their own channels. The deps channel is for third-party dependencies; internal code is just more source channels with different visibility.

Default history: lockfile — the lock IS the history. You don't need upstream's git history; you need the resolution result with content hashes.

artifacts Artifacts

Built outputs. Binaries, container images, WASM modules, generated PDFs, signatured release tarballs. Content-addressed, signed, immutable.

Why content-addressed: an artifact is a function of its inputs (source + deps + environment). If the function is deterministic, the same inputs always produce the same artifact, and the hash is the identity. If the function isn't deterministic, you still get a hash — it's just a less useful one for verification.

Why signed: because pulling a binary from "the internet" without provenance is the supply-chain attack. Every artifact ships with a signed manifest that says "I was built from src@X + deps@Y + env@Z by maintainer K."

Why immutable: a v1.2.3 binary shouldn't change after release. If you want a new binary, push a new artifact with a new ref. This is the property that makes rollback trivial.

Default history: ring(10) — the last 10 signed manifests are kept for rollback. You don't need a DAG of every build ever; you need the last few in case the latest one is bad.

⏳ History as an axis

The single biggest mental shift from git: history is a property of a channel, not of a project. Git treats history as a single immutable DAG that contains everything. k33p treats history as a per-channel configuration knob.

Channel Default history Why
src full You want to bisect, blame, and see who broke what.
private none Secrets shouldn't leave a history trail. Rotation replaces them.
deps lockfile The lock IS the history. You don't need upstream's git log.
artifacts ring(N) You need the last few for rollback, not the whole DAG.

And per role, you can change the default:

  • A developer doing PRs wants src@shallow — fast clone, just the tip of each branch.
  • A maintainer wants src@full — blame, signed tags, history search.
  • A user wants src@none — no source at all, just artifacts.
  • A CI runner wants src@shallow + private@read-only + artifacts@latest.

History policy lives in two places: the channel default in k33p.yaml, and the role override. The role override wins. This makes the system configurable without per-machine fiddling.

👥 Roles & materialized views

Roles are the UX layer. They answer "what does a person (or an agent) with role X need on disk?" with a single line in the manifest.

The five defaults a project gets for free, unless it overrides them:

end-user

channels: artifacts
Just wants to run the thing. Pulls binaries, no source, no history.

developer

channels: src deps
Wants to build and modify. Shallow src + vendored deps. No secrets.

maintainer

channels: src private artifacts
Owns the project. Full src, has secrets, signs builds, publishes.

ci

channels: src deps private
Builds and publishes. Reads secrets to sign artifacts, never writes them.

auditor

channels: src artifacts
Verifies provenance. Full history, strict signature checks, no write access.

Custom roles are first-class: release-engineer, docs-writer, intern, agent-bot. A role is just a named bundle of channel subscriptions + history settings. Nothing magical.

Switching roles is one command:

$ k33p role
  current: developer
$ k33p role use maintainer
  → fetching private@latest
  → fetching artifacts@latest
  → upgrading src to history=full
$ k33p role
  current: maintainer

🪪 Provenance & signing

For every artifact, k33p produces a signed build manifest that links inputs to outputs. The manifest is the project's "software bill of materials," built into the system, not bolted on.

# .k33p/artifacts/manifests/v1.2.3.manifest.yaml
artifact:     sha256:abc123...           # the binary
source:
  channel:    src
  ref:        v1.2.3
  commit:     deadbeef...
  signed_by:  age1maintainer...
dependencies:
  channel:    deps
  lock:       sha256:def456...
environment:
  image:      ubuntu:24.04
  rust:       1.79.0
  env_hash:   sha256:789abc...
build:
  runner:     ci-runner-pool-1
  started:    2026-06-17T10:11:12Z
  finished:   2026-06-17T10:18:43Z
signature:
  key:        age1releasekey...
  sig:        sig1xyz...

This makes several things possible that are currently heroic:

  • Verify an artifact by checking the signature on its manifest, then checking the manifest's claimed inputs (src commit, dep lock) match what's in your lockfile.
  • Reproduce a build by checking out the exact src commit, vendoring the exact dep lock, and running the same build in the same env.
  • Track a binary back to a person via the signing key.
  • Detect drift — if an artifact was rebuilt from different inputs than its manifest claims, the hash won't match.

Multi-sig for sensitive channels (private, artifact publish) is a v1 feature: a release can require N of M maintainer signatures to publish.

🛰️ Offline-first & mirroring

Everything is content-addressed. That's not a stylistic choice; it's load-bearing for the offline story.

  • A mirror is a subset of content-addressed objects. No semantic difference from the primary. k33p mirror ./offline k33p://coolproject@v1.0 copies what fits on the drive.
  • Partial mirrors are first-class. You can mirror just the artifacts channel (a "binaries disk") or just the deps channel (a "vendored deps disk") or just src (a "source backup").
  • A USB stick with src + deps for coolproject@v1.0 = a buildable snapshot you can take on a plane. k33p clone /media/usb/offline works without internet.
  • Determinism is rewarded. When src+deps+env is deterministic, a mirrored artifact is byte-identical to a freshly-built one. Mirror once, verify forever.

🔌 Compatibility with git

k33p doesn't replace git for the source channel. It wraps it. This is the single most important decision in the design: migration cost has to be near-zero or no one will adopt it.

  • k33p init --from-git <url> wraps an existing git repo in a k33p project. The .git/ directory is unchanged.
  • k33p git <args...> passes through to git for the source channel. All existing muscle memory works.
  • k33p.yaml is just a file in the repo. Committed, reviewed, signed — like any other file.
  • Existing CI (GitHub Actions, GitLab CI, Buildkite) keeps working. The CI's role is ci; it does k33p sync instead of git pull, and the rest is unchanged.
  • Existing tooling that reads .git/ directly (IDEs, blame tools, merge drivers) keeps working. k33p is a layer above, not a replacement.

You adopt k33p one channel at a time:

  1. Add k33p.yaml to your repo. src is git, just declared.
  2. Add an artifacts channel. Push your release binaries as OCI objects with signed manifests.
  3. Add a deps channel. Vendoring becomes a k33p concern, not a custom CI script.
  4. Add a private channel. Secrets stop living in .env checked into a Slack thread.

At every step, the project is more k33p and less of a glue job. You stop wherever you stop. There's no "v2 migration" cliff.

⌨️ Command surface

# project lifecycle
k33p init [--from-git URL] [--template ROLE]
k33p clone URL [DIR]                  # clone by default role
k33p clone URL --role=end-user        # clone for end users
k33p sync                             # update all subscribed channels
k33p lock [--update]                  # regenerate k33p.lock

# roles
k33p role [show | use <name> | list] # switch role

# channels
k33p channel list | show | add | remove
k33p channel get <name>[@<ref>]       # fetch a specific channel
k33p channel push <name>              # publish a channel

# trust & provenance
k33p sign <channel>                   # sign content
k33p verify [--strict]                # verify signatures and provenance

# execution
k33p exec -- <command>                # run with secrets mounted

# distribution
k33p mirror [TARGET] [URL]            # create/apply a mirror
k33p rollback <ref>                  # roll back to a locked state

# pass-through
k33p git <args...>                    # pass through to git for src

Every command works offline against a mirror. There is no "I need to phone home" state for the common cases.

🗂️ Project layout

coolproject/                      # k33p project root
├── k33p.yaml                     # project manifest (committed to src)
├── k33p.lock                     # cross-channel lock (committed or not, by policy)
├── README.md
├── .git/                         # src channel — a real git repo
├── .k33p/                        # k33p metadata (gitignored)
│   ├── private/                  # encrypted secret blobs
│   ├── deps/                     # vendored dependencies (when fetched)
│   ├── artifacts/                # pulled artifacts (when fetched)
│   ├── manifests/                # signed build manifests
│   └── cache/                    # transfer state, partial mirrors
└── src/                          # source code (managed by git)

The .k33p/ directory is gitignored. Everything inside it is materialized by k33p based on the active role and lock. Deleting it is safe — it's a cache, not a source of truth.

The lock file is committed by default for projects that care about reproducibility (binaries, builds, audits). For projects where the lock changes too often to commit, it can be marked gitignored in the manifest.

🛡️ Security model

Threat Mitigation
Secret leakage in public repo Impossible by construction. Secrets live in an encrypted channel, not a file in the source tree.
Dependency confusion attack Dependencies pinned by content hash; lockfile is signed; resolution is reproducible.
Backdoored artifact Re-build from signed source + deps + env; the manifest claims specific inputs, the build can verify them.
Stolen credentials Hardware-backed keys (age + YubiKey, SSH agent, OS keychain); audit log of every decryption.
Rogue maintainer Multi-sig for sensitive channels (private rotation, artifact publish). Quorum + threshold.
Compromised mirror Content addressing + signatures. A mirror is a subset of signed objects; partial corruption is detectable.
Replay of old manifest Lockfile is signed; verifying a manifest against the current lock is a strict operation.

The most important property: the secret channel is structurally incompatible with the public channel. You cannot accidentally put a secret in source, because secrets don't have paths in source. The most common class of breach in modern projects becomes a type error.

🎬 Concrete scenarios

1. End user installs a CLI

$ k33p get coolproject@latest --role=end-user
  → fetches artifacts channel only
  → verifies signature against known maintainer keys
  → installs coolproject binary to ~/.local/bin
$ # never touched src, deps, secrets, or git history
$ du -sh .k33p/
  12M

2. Developer clones to fix a bug

$ k33p clone coolproject --role=developer
  → fetches src (shallow) + deps (vendored, locked)
  → no history, no artifacts, no secrets
$ du -sh .
  48M    # vs 1.2G for a full git clone + unvendored deps

3. CI builds and publishes

$ k33p sync --role=ci
  → src@shallow, deps@latest, private@RO
$ cargo build --release
$ k33p sign artifacts --inputs src@<commit>,deps@<lock>
  → publishes signed build manifest + artifacts

4. Auditor reviews a release

$ k33p clone coolproject@v1.2.3 --role=auditor
  → src@full, artifacts@full
$ k33p verify --strict
  ✓ src signature valid
  ✓ deps lock matches signed lock
  ✓ artifact signature valid
  ✓ build manifest links to verified src commit

5. Offline dev on a plane

# before the flight
$ k33p mirror ./offline coolproject@v1.0 --role=developer
  → copies src + deps + lockfile to ./offline
$ cp -r offline/ /media/usb/

# on the plane
$ k33p clone /media/usb/offline
  → full reproducible environment, zero internet
$ cargo build --release
  → builds, because deps are vendored

6. Maintainer rotates a leaked API key

# leak happens; new key issued
$ k33p private set STRIPE_API_KEY <new-value>
  → encrypts with maintainer recipients
  → publishes new content-hashed blob to the private channel
  → old blob still exists (rotation doesn't rewrite history, by design)
  → but apps reading from the channel see the new value, because refs point to the latest

# verify the rotation worked
$ k33p exec -- env | grep STRIPE
  STRIPE_API_KEY=<new-value>

❓ Open questions

These are the design decisions I haven't made yet. Calling them out honestly so the design can be critiqued on its weakest joints.

Mutable refs in artifacts. Some artifacts (a website, a wiki page, a "latest" symlink) change in place. Model as a live sub-channel with a TTL? Or treat as a separate live channel type? Or punt to the consumer?
Derived content. Docs from source, schemas from source, generated protobuf, type stubs. Build pipeline or its own channel? My instinct: build pipeline. The artifact IS the derived content; the build manifest records the derivation.
Federation. A project on multiple forges (github + gitlab + self-hosted). Mirror? Multi-primary? Local views with promotion? My instinct: single source of truth per channel + read-only mirrors. Like git remotes, but for channels.
Migration from monorepos. How do you split a giant existing repo into k33p channels? Tools, or convention? A k33p split command that takes a path prefix and turns it into a channel?
Multi-tenancy. Org-level k33p projects with per-team channels and cross-team secrets. An "organization" is a project whose channels are other projects?
Discovery. A k33p search over public project channels (like crates.io for everything). Who runs the index? Decentralized via signed manifests, or a central service?
Economics. Artifact storage is expensive. Who pays? Built-in cost model? Paid transports? "Bring your own bucket"?
Legal / jurisdiction. Where does a k33p server live? GDPR for the private channel? Compliance with export controls? This is the unsexy part of the design but it's where many "obvious" architectures fall over.
Lock vs. tag. When a maintainer says "v1.2.3," is that a lock or a tag? My instinct: a tag points to a lock. The lock is machine-readable and content-addressed; the tag is human-friendly and signed. Same idea as git tags pointing to commits, but for the whole project.

🔤 Why "k33p"

  • keep — keep your code, keep your secrets, keep your builds. The verb says what the system does.
  • 33 — three threes, or "eee" — keep everything. The digits are playful, not pretentious.
  • Four characters — same shape as git, hg, svn. CLI-friendly. Stands out from a list of long names.
  • Lowercased — like a tool, not a brand. A verb that happens to be a noun.
  • Spellable on a phone — important for typing into a terminal over a remote shell.
