k33p — typed version control for the real shape of a project

One URL. Content-addressed store. Channels, views, and a daemon that does the boring parts.

Status: design draft · v0.3 · lives at ideas/k33p/design.html

Thesis. A modern project is not a git repository with some bag of side channels bolted on. It is a content-addressed store projected through typed channels onto role-based views, with a daemon that handles the parts humans shouldn't have to. Public source, private content, third-party dependencies, and built artifacts are four different content kinds with four different rules; the only thing they share is the project name. Most real projects are monorepos with many subprojects, each with its own secret keys, dependency set, build outputs, and release cadence — and k33p treats subprojects as the unit of consumption, so any consumer — human, CI, mirror — can pull exactly the slice they need, with mutable pointers where they're useful and immutable history everywhere else.

🧩 The problem

An open source project has four distinct content kinds. Git handles one of them well.

Content kindExampleWhat owns it today
src Application code, tests, docs git on github/gitlab/sourcehut
private .env, API keys, internal notes, sensitive code paths …a prayer, plus a .gitignore
deps Third-party libraries, transitive lockfile npm / cargo / pip / oci, separately
artifacts Binaries, container images, generated PDFs, derived docs CI artifact store, ghcr.io, releases page

And four kinds of consumers, each wanting a different slice:

  • End user — wants the binary, doesn't want the source on disk at all.
  • Developer — wants source + dependencies, doesn't want 1.2 GB of git history.
  • Maintainer — wants source + secrets + history + the ability to sign a release.
  • Auditor / supply-chain reviewer — wants signed manifests and full history.
The current answer is a fragile glue job: .env.example checked in, secrets stored in 1Password, a CI script that wires it all together, a separate container registry for artifacts, a separate lockfile for deps, and a strong cultural rule that nobody ever accidentally commits a credential. On top of that: the developer has to remember to commit, the CI has to remember to tag, the release page has to be updated by hand, and a "latest" pointer is a mutable string someone can overwrite. This is not version control. It's an honor system with a few automation scripts.

k33p's answer: type the channels, make the on-disk layout configurable per role, add a daemon that does the boring parts, and content-address everything so mirrors are trustless and reproducibility is local.

🧱 Core abstractions

k33p has ten concepts. They're cheap on their own; the design is in how they compose.

1. Project

A name, a manifest (k33p.yaml), a set of channels, and an optional cross-channel lock (k33p.lock). The thing a person points at with one URL.

2. Store

A content-addressed object store shared by every channel in a project. Like git's .git/objects, but channel-agnostic: a blob, a commit, a secret, a dep tarball, an artifact — anything in k33p is an object in the store, addressed by its hash. This is the single most important design move. It gives k33p:

  • Dedup for free — the same blob used in two channels is stored once.
  • Trustless mirrors — a peer serves content by hash; verification is local.
  • Object-level addressing — you can pin a single hash, not a whole channel state.

3. Channel

A typed view over the store. Each channel has a type (source, secrets, dependencies, artifacts, or live), a transport (where its bytes come from), an access policy, a history policy, and a retention policy. Channels are independent — a secret channel knows nothing about a source channel, except that the manifest points them at the same project.

4. View

A per-role projection of channels onto disk paths. Instead of a fixed .k33p/private/, .k33p/deps/, etc., a view says "the private channel's content hash X materializes at .env; the deps channel materializes at ./node_modules; the artifacts channel materializes at ./build/." Different roles can have different views. The store is canonical; the working tree is computed.

5. Ref

A pointer to a specific state in a channel. For source: a commit SHA, a tag, a branch. For secrets: a content hash. For deps: a lockfile revision. For artifacts: a signed manifest ID. Refs are immutable in the src / private / deps / artifacts channels — once a ref points at an object, it always points at that object.

6. Pointer

A ref in the live channel that can change. A pointer maps a human-friendly name to a ref in another channel. latest, canary, main, dev — these are pointers, not commits. Pointers are the only mutable thing in the system.

7. Role

A named bundle of channel subscriptions + view definition + history settings. The UX win: a user picks a role and k33p materializes exactly the view that role defines. end-user, developer, maintainer, ci, auditor ship as defaults.

8. Lock

k33p.lock pins every channel to a specific ref and records the full toolchain used to build: compiler, build system, linker, codegen options, environment hash, source commit, dep lock, and the signature of whoever made the lock. Reproducible builds depend on the lock being exact; "I built it on my machine" is no longer an excuse.

9. Daemon

A long-running k33p process that watches source directories, debounces edits, runs pre-commit hooks, and creates an auto-commit after some period of inactivity. Also runs a content-addressed cache for partial mirrors, and can serve objects to peers. The daemon is opt-in and per-project; without it, k33p works exactly like a manual VCS.

10. Org / Team

Multi-tenancy primitive. An org owns projects and has nested teams, which themselves can have sub-teams. Permissions cascade down the tree. A team can have its own private channel that only that team can see. Orgs and teams are first-class addressable entities (k33p://acme/backend/api/coolproject).

11. Subproject

The unit of consumption inside a monorepo. A subproject is a path-scoped slice of a parent project with its own k33p.yaml (or inherited from the parent), its own view, its own channel subscriptions, and its own lockfile. A k33p "project" is just a monorepo with one or more subprojects; a "single project" is a monorepo with one subproject at the root path. Subprojects can declare their own private, deps, and artifacts channels — all keyed to the subproject's path — so a secret for powder_play is a different secret than one for full_auto_ci, even though they live in the same monorepo. The URL scheme is k33p://<monorepo>/<subproject>.

📜 The manifest

Every project carries a k33p.yaml at its root, committed to the source channel like any other file. It declares channels, views, roles, and the daemon config. A real example:

# k33p.yaml — committed to the src channel
project: coolproject
org: acme/backend/api
description: A thing that does stuff

# ── channels: typed content streams ──────────────────────────
channels:
  src:
    type: source
    transport: git+https://github.com/coolproject/coolproject
    visibility: public
    history: full

  private:
    type: secrets
    transport: k33p+https://secrets.acme.com/coolproject
    encryption: age
    recipients: ["maintainers@acme.com"]
    history: none

  deps:
    type: dependencies
    transport: oci+https://registry.acme.com/coolproject-deps
    resolver: cargo
    pinned: true
    history: lockfile

  artifacts:
    type: artifacts
    transport: oci+https://registry.acme.com/coolproject
    content_addressed: true
    signed: true
    history: ring(10)

  live:
    type: live
    transport: k33p+https://live.acme.com/coolproject
    pointers:
      latest-stable: artifacts@v1.2.3
      canary:        artifacts@ci-2026-06-17-101112
      main:          src@main
    update_policy:
      max_per_hour: 10
      signed_by:    [release-key]

# ── views: per-role mapping of channels to disk paths ────────
views:
  default:
    src:        { at: "./" }
    deps:       { at: "./node_modules" }
    artifacts:  { at: "./build/" }
  developer:
    extends: default
    src:     { at: "./", history: shallow }
    deps:    { at: "./node_modules", vendored: true }
  maintainer:
    extends: default
    src:        { at: "./", history: full }
    private:    { at: "./.env" }            # materialized in the working tree
    artifacts:  { at: "./build/" }
  ci:
    extends: default
    src:        { at: "./", history: shallow }
    deps:       { at: "./.k33p/vendored/" }
    private:    { at: "env", mount: true }  # mounted into subprocess env, never on disk
    artifacts:  { at: "./build/" }
  end-user:
    artifacts:  { at: "~/.local/bin/", install: true }

# ── roles: named bundles of view + channels + permissions ──
roles:
  end-user:    { view: end-user }
  developer:   { view: developer }
  maintainer:  { view: maintainer, publish: [src, private, artifacts, live] }
  ci:          { view: ci,        publish: [artifacts, live] }
  auditor:     { view: default,   history: full, verify: strict }

# ── daemon: auto-commit, hooks, mirrors ─────────────────────
daemon:
  auto_commit:
    enabled: true
    debounce: 5m
    paths: [src/, docs/]
    ignore: ["*.tmp", "*.swp", ".*.un~"]
    message: "auto: changes in {files}"
    pre_commit: ./scripts/pre-commit.sh
    push_after: 15m

# ── multi-tenancy: org/team context ─────────────────────────
org: acme
team: backend/api
visibility:
  private: team
  src: public

Five properties to notice:

  1. Views replace fixed channel folders. A developer view puts deps at ./node_modules; a ci view puts them at ./.k33p/vendored/; an end-user view doesn't materialize the deps channel at all. No required on-disk layout.
  2. History is per-channel and per-view. A developer view can override src.history: shallow even if the channel default is full.
  3. Mutable refs live in one place. The live channel is the only place where pointers change. src, private, deps, and artifacts are always immutable per ref.
  4. Roles are bundles, not permissions. A role names a view plus optional publish capabilities. Authorization is a transport-level concern.
  5. The daemon is declarative. Auto-commit rules live in the manifest, not in a CI YAML. They travel with the project.

📦 The five channels

Five channel types. Four are content; the fifth (live) is pointers. Each is a different kind of thing with different storage, transport, and rules.

src Source

The classic version-controlled code. Backed by git; k33p is a thin wrapper, not a replacement. Visibility is public by default (matches the user's mental model of "an open source project"), but visibility: private works for closed source. Git's own object store is referenced from the k33p CAS by hash; nothing is duplicated.

Why git: it's not perfect, but it's universal, well understood, and battle-tested. The cost of replacing it is enormous and the win is small. The live channel can still point at a branch like src@main, so the k33p model treats git as a source of pointer-able refs.

Default history: full for maintainers, shallow for developers and CI, none for end users (they don't have this channel at all).

private Secrets

Encrypted at rest, encrypted in transit, encrypted in any cache. Each blob is its own ciphertext, content-addressed, addressed by content not by path. Rotating a secret means re-encrypting, not rewriting history — because there is no history.

Why a separate channel: a .env file is not a "file" in the source sense. Its lifetime is "now," not "v1.0.0." Its access model is "decrypt with key X," not "clone over HTTPS." Putting it in the source channel is what causes every secret leak in the wild.

Decryption keys live in the OS keychain, on a hardware token, or behind an SSH agent. They are never committed, never on disk in plaintext, never in the source channel.

On disk: a view chooses. A maintainer view materializes the active secret blob at ./.env. A ci view mounts decrypted values into the subprocess environment without writing to disk. An end-user view doesn't materialize this channel at all.

Default history: none. Always.

deps Dependencies

Third-party code the project depends on, pinned by content hash. A lockfile (the resolution) and a blob store (the resolved bytes), treated as one channel.

Transports: any package ecosystem is a valid transport. Cargo, npm, pip, Go modules, OCI, Nix flakes. k33p doesn't replace them; it wraps them. The transport field says "I use cargo"; k33p shells out to cargo for resolution and re-uses its lockfile as the k33p ref.

Vendoring is a view choice. A developer view materializes deps at ./node_modules (the conventional path). A ci view materializes them at ./.k33p/vendored/ (off to the side). Either way, the CAS holds them by content hash; the view is a layout choice.

Project-specific deps (a forked internal library, a private package) live in their own channels. The deps channel is for third-party dependencies; internal code is just more source channels with different visibility.

Default history: lockfile — the lock IS the history. You don't need upstream's git history; you need the resolution result with content hashes.

artifacts Artifacts

Built outputs. Binaries, container images, WASM modules, generated PDFs, derived docs, generated protobuf, type stubs — anything the build produces. Content-addressed, signed, immutable per artifact.

Derived content lives here. If your docs are generated from source, the generated HTML is an artifact. The build manifest records the derivation: (src@commit, deps@lock, toolchain, env) → artifact@hash. Consumers don't have to rebuild to consume — they pull the artifact by hash and the build manifest tells them how it was made.

Why content-addressed: an artifact is a function of its inputs (source + deps + toolchain + environment). If the function is deterministic, the same inputs always produce the same artifact, and the hash is the identity. If the function isn't deterministic, you still get a hash — it's just a less useful one for verification.

Why signed: because pulling a binary from "the internet" without provenance is the supply-chain attack. Every artifact ships with a signed manifest that says "I was built from src@X + deps@Y + env@Z by maintainer K."

Why immutable per artifact: a v1.2.3 binary shouldn't change after release. If you want a new binary, push a new artifact with a new ref. Mutable pointers to artifacts live in the live channel — not here.

Default history: ring(10) — the last 10 signed manifests are kept for rollback. You don't need a DAG of every build ever; you need the last few in case the latest one is bad.

live Live (pointers)

The only mutable channel. A live channel holds pointers: human-friendly names mapped to refs in other channels. latest-stable → artifacts@v1.2.3; canary → artifacts@ci-2026-06-17-101112; main → src@main.

Pointers are not refs to objects in this channel. They are refs to other channels' refs. The live channel itself contains only signed pointer updates — every change is a new immutable signed object that says "as of time T, latest-stable now points to artifacts@v1.2.3."

Why a separate channel: because src, private, deps, and artifacts are immutable per ref, and the rule "immutable per ref" is the property that makes everything else work. Mutable behavior lives in exactly one place so it can be audited, rate-limited, and signed.

Rate limits and signing: a live channel declares update_policy.max_per_hour and update_policy.signed_by. A latest-stable pointer that moves ten times an hour is broken; the rate limit catches it. A pointer move signed by an unauthorized key is rejected; the signature catches it.

Default history: ring(50) — keep the last 50 pointer updates for audit ("who moved latest to what, when?").

🔁 Mutable references

The single most-confused concept in version control: what does "mutable" mean, and where is it allowed?

k33p's answer: mutable references are the contents of the live channel, and only the live channel. Everything else is immutable per ref. The rule is enforced by the type system — a src ref can never change; if you want a different commit, you add a new commit, you don't rewrite the old one.

Why this matters. Most "version control" systems have one mutable thing — a branch ref — and every other system (tags, releases, "latest") either aliases to that mutable thing or is informally updated. The result: an attack on main rewrites history for everyone; a typo'd release tag gets silently moved; "latest" points to whatever someone last pushed. k33p's separation: immutable history is the default, mutable pointers are opt-in, and pointer moves are themselves signed, rate-limited, and auditable events.

Pointer updates as signed events

Every pointer change is a new signed object in the live channel:

# An example pointer update
pointer: latest-stable
previous: artifacts@v1.2.2
new:      artifacts@v1.2.3
author:   release-bot
timestamp: 2026-06-17T19:00:00Z
reason:   release v1.2.3
signature:
  key: age1releasekey...
  sig: sig1xyz...

The previous value is recorded, so audit logs are complete. The signature is required, so a hijacked CI runner can't move latest-stable on a whim.

What the live channel is for

  • Release pointers — latest, latest-stable, lts, canary.
  • Branch pointers — main, develop, next. (These are the only mutable refs in src, and they live in live so the immutability of src stays clean.)
  • Per-consumer pointers — @user:my-fork, @ci:current-run.
  • Live deployments — production → artifacts@v1.2.3; staging → artifacts@ci-latest.

What the live channel is NOT for

  • Storing content. If you need a content blob, it goes in another channel.
  • Replacing a build manifest. The pointer says "which artifact"; the manifest says "how it was built."
  • Editing the past. Pointer updates don't rewrite history; they add events.

⏳ History as an axis

The single biggest mental shift from git: history is a property of a channel, not of a project. Git treats history as a single immutable DAG that contains everything. k33p treats history as a per-channel (and per-view) configuration knob.

ChannelDefault historyWhy
src full You want to bisect, blame, and see who broke what.
private none Secrets shouldn't leave a history trail. Rotation replaces them.
deps lockfile The lock IS the history. You don't need upstream's git log.
artifacts ring(N) You need the last few for rollback, not the whole DAG.
live ring(50) Pointer updates are auditable events; you want the last 50.

And per view, you can change the default:

  • A developer doing PRs wants src@shallow — fast clone, just the tip.
  • A maintainer wants src@full — blame, signed tags, history search.
  • A user wants src@none — no source at all, just artifacts.
  • A CI runner wants src@shallow + private@mount + artifacts@latest-pointer.

👥 Roles & views

Roles are the UX layer. They answer "what does a person (or an agent) with role X see on disk?" with a single line in the manifest.

The five defaults a project gets for free, unless it overrides them:

end-user

channels: artifacts
Just wants to run the thing. View: ~/.local/bin/, install mode. No source, no history.

developer

channels: src deps
Wants to build and modify. View: ./ for src, ./node_modules for deps. Shallow src, vendored deps. No secrets.

maintainer

channels: src private artifacts
Owns the project. Full src, .env materialized, signs builds, publishes. Has the daemon running locally for auto-commit.

ci

channels: src deps private
Builds and publishes. Reads secrets via env mount, never writes them. Vendor path is ./.k33p/vendored/. Publishes to artifacts + live.

auditor

channels: src artifacts live
Verifies provenance. Full history, strict signature checks, full pointer audit trail, no write access anywhere.

Custom roles are first-class: release-engineer, docs-writer, intern, agent-bot, etc. A role is just a named view plus optional publish capabilities.

Switching roles

$ k33p role
  current: developer
$ k33p role use maintainer
  → unmounting ./node_modules (deps)
  → mounting ./.env (private)
  → upgrading src history to full
  → daemon: starting
$ k33p role
  current: maintainer

The role switch is non-destructive: the canonical state is the store, not the working tree. Switching back to developer just unmounts private and re-shallowens src.

🌳 Subprojects & monorepos

Most real projects are not single repos. They are monorepos — a single git history that contains many subprojects, each with its own lifecycle, its own secret keys, its own dependency tree, and its own release cadence. k33p's first-class citizen is the monorepo. A "single project" is a degenerate case: a monorepo with exactly one subproject rooted at /. Every k33p concept (channels, views, roles, locks, the daemon) composes the same way whether a project has one subproject or fifty.

Why this matters. Most version control systems treat the monorepo as a worst case: huge, slow, full of unrelated code. The monorepo owner is told to "split into separate repos." k33p flips that: the monorepo is the normal case, and a subproject is a slice you can pull, build, sign, and ship independently. The git history stays unified. Permissions stay centralized. But every consumer only pays for the slice they need.

The subproject model

A subproject is a path-scoped slice of a parent project with:

  • A path in the parent (e.g., active/games/powder_play/).
  • An optional own k33p.yaml at that path. If absent, the subproject inherits the parent's manifest and behavior.
  • Its own view (where channels materialize on disk).
  • Its own channel subscriptions — private, deps, artifacts, live can all be subproject-scoped.
  • Its own lockfile — k33p.lock at the subproject path, pinning the subproject's refs and toolchain.
  • Its own daemon config — auto-commit rules can be different per subproject.

A path-scoped channel works like this: a private blob encrypted for powder_play is a different blob than one encrypted for full_auto_ci, because the channel's scope: key namespaces the channel content by subproject path. The encryption recipients, the audit log, the signing key — all scoped to the subproject.

The manifest: single-project vs monorepo

The same k33p.yaml format works in both modes. A single-project k33p.yaml is just a monorepo manifest with one subproject implicit at the root path. A monorepo k33p.yaml adds a subprojects: block:

# k33p.yaml at the monorepo root — megarepo/k33p.yaml
project: megarepo
type: monorepo
org: calvinloveland
description: A consolidated monorepo for active projects, shared tooling, and docs.

# ── monorepo-wide channels ─────────────────────────────────
channels:
  src:
    type: source
    transport: git+https://github.com/calvinloveland/megarepo
    visibility: public
    history: full
  private:
    type: secrets
    transport: k33p+https://secrets.calvinloveland.dev/megarepo
    encryption: age
    recipients: ["maintainers@calvinloveland.dev"]
    history: none
    scope: monorepo            # the monorepo-wide private channel

# ── subprojects: path-scoped slices ────────────────────────
subprojects:
  powder_play:
    path: active/games/powder_play/
    description: A falling-sand game with LLM-generated materials.
    channels:
      private:
        scope: active/games/powder_play/
        transport: k33p+https://secrets.calvinloveland.dev/powder_play
        recipients: ["games-team@calvinloveland.dev"]
      deps:
        scope: active/games/powder_play/
        transport: oci+https://registry.calvinloveland.dev/powder_play-deps
        resolver: npm
      artifacts:
        scope: active/games/powder_play/build/
        transport: oci+https://registry.calvinloveland.dev/powder_play
    daemon:
      auto_commit:
        debounce: 2m           # tighter debounce for fast iteration

  full_auto_ci:
    path: active/dev-tools/full-auto-ci/
    description: Fully automatic continuous integration.
    channels:
      private:
        scope: active/dev-tools/full-auto-ci/
      deps:
        scope: active/dev-tools/full-auto-ci/
        resolver: pip
      artifacts:
        scope: active/dev-tools/full-auto-ci/dist/

  docs:
    path: docs/
    description: Repository-wide documentation site.
    channels:
      artifacts:               # the published site is a build artifact
        scope: docs/site/
        transport: oci+https://registry.calvinloveland.dev/megarepo-docs

Each subproject's k33p.yaml can also live at the subproject path, augmenting the parent:

# megarepo/active/games/powder_play/k33p.yaml
# This augments (not replaces) the monorepo's k33p.yaml.
subproject: powder_play
extends: ../../../k33p.yaml      # explicit inheritance pointer

views:
  default:
    src:       { at: "./" }
    deps:      { at: "./node_modules" }
    artifacts: { at: "./build/" }
  ci:
    extends: default
    src:       { at: "./", history: shallow }
    deps:      { at: "./.k33p/vendored/" }
    private:   { mount: "env" }     # secrets via env, never on disk

The two-file layout (parent manifest + per-subdir manifest) is optional. A monorepo can put everything in the root manifest. The per-subdir manifest is for projects that want the configuration to live next to the code it configures.

The URL scheme

k33p://megarepo/                              # the monorepo
k33p://megarepo/powder_play                   # a subproject (slash form)
k33p://megarepo/games/powder_play             # full path form
k33p://megarepo/powder_play@v1.2.3            # at a tag
k33p://megarepo/powder_play@deadbeef          # at a commit
k33p://megarepo/powder_play@deadbeef#private  # a specific channel

Short names (powder_play) and full paths (games/powder_play) are interchangeable when unambiguous. Subprojects must have unique short names within a monorepo.

Pulling a subproject: the unit of consumption

$ k33p clone megarepo/powder_play
  → src: scope=active/games/powder_play/, materialized at ./
  → deps: powder_play-scoped deps at ./node_modules
  → private: powder_play-scoped secrets at ./.env (if you have rights)
  → artifacts: powder_play-scoped artifacts at ./build/
  → ignores the rest of the monorepo (47 other subprojects)
$ du -sh .k33p/store/
  48M    # the slice, not the whole monorepo

What just happened: the src channel was fetched with a path scope. The CAS contains the full monorepo's objects (so the subproject's view is consistent with the monorepo state), but the working tree only contains the active/games/powder_play/ subtree. The private channel fetched only the powder_play-scoped secrets. The deps channel fetched only the powder_play-scoped deps. The other 47 subprojects' content is in the store (because git objects are immutable and shared), but it never materializes on disk.

Subproject commands

# discover
k33p list <monorepo>                       # list all subprojects
k33p show <monorepo>/<subproject>         # show subproject config + state

# clone / sync
k33p clone <monorepo>/<subproject>        # clone a subproject
k33p clone <monorepo>                      # clone the whole monorepo
k33p sync                                   # pull updates for the current subproject

# create / move / delete
k33p subproject add <name> --path <path>    # add a new subproject
k33p subproject move <name> --to <newpath>  # move a subproject in the tree
k33p subproject remove <name>              # remove a subproject (keeps history)
k33p subproject rename <old> <new>          # rename a subproject

# convert
k33p split <monorepo>/<subproject>         # split a subproject into a standalone project
k33p merge <standalone> --into <monorepo>  # merge a standalone project into a monorepo

Cross-subproject references

Subprojects inside the same monorepo can reference each other. The most common case: a "library" subproject shared by several "app" subprojects. The reference goes through the artifacts channel, content-addressed:

# in active/web-apps/cool-app/k33p.yaml
subproject: cool-app
channels:
  deps:
    # depend on a published artifact from another subproject in the
    # same monorepo. content-addressed, so the build is reproducible.
    from:
      - subproject: shared-ui-library
        artifact: shared-ui@v1.4.2
        transport: oci+https://registry.acme.com/shared-ui

Why go through artifacts and not raw source? Because the artifact is signed, content-addressed, and reproducible. A library maintainer who publishes shared-ui@v1.4.2 to the artifacts channel has produced a signed build manifest that says "this artifact was built from shared-ui@commitX with toolchain Y." The consuming app can verify the build before depending on it, and the dependency is pinned to a specific artifact hash, not a moving branch ref.

Shared deps across subprojects

Two flavors of dependency in a monorepo:

  • Shared deps — common libraries used by many subprojects. The monorepo can declare a shared-deps subproject that owns them; other subprojects reference shared-deps's artifacts.
  • Per-subproject deps — deps used by only one subproject. These live in that subproject's deps channel and don't leak to siblings.

The split is declarative — the monorepo's manifest decides which deps are shared and which are per-subproject. There's no "I accidentally imported from another subproject" footgun, because cross-subproject imports go through signed artifacts, not raw source.

Per-subproject roles & permissions

A team can be granted access to a subproject, not the whole monorepo:

# at k33p://acme/backend/api/megarepo
$ k33p org grant --to acme/games-team --subproject powder_play
  → games-team can read+write src, private, deps, artifacts, live
  → games-team cannot see other subprojects (sibling privacy)
$ k33p org grant --to acme/sre --subproject '*' --read-only
  → sre can read every subproject for ops purposes
  → sre cannot write anywhere

The permissions cascade: a team with access to the monorepo can be allowed to see specific subprojects. A team with access to a subproject inherits the subproject's channel permissions, scoped to that subproject only.

The "single project" case

A standalone k33p project is just a monorepo with one subproject implicit at the root. The implicit subproject is named after the project and lives at the path /. Its k33p.yaml is the project's manifest — no extra file, no extra config.

When you k33p init --from-git <url> on a non-monorepo git repo, k33p creates a single-subproject manifest with no subprojects: block. Everything works the same. If you later want to add a second subproject, you add it to the manifest and it just works.

Conversely, a subproject can be split into a standalone project: k33p split megarepo/powder_play creates a new project with its own k33p.yaml, its own channels, and a history that's preserved from the monorepo. The monorepo loses the subproject; the new project gains it. Nothing about the git history is rewritten.

👁️ The k33p daemon

The boring parts of development: remembering to commit, remembering to push, running the same pre-commit hooks every time, retrying a flaky CI job, syncing a partial mirror. The daemon does these.

Auto-commit

The daemon watches configured paths in the source channel, debounces edits, runs pre-commit hooks, and creates a commit after a period of inactivity. Configuration lives in the manifest:

daemon:
  auto_commit:
    enabled: true
    debounce: 5m              # commit after 5 minutes of no edits
    paths: [src/, docs/]
    ignore: ["*.tmp", "*.swp", ".*.un~", "build/"]
    message: "auto: changes in {files}"
    pre_commit: ./scripts/pre-commit.sh
    push_after: 15m           # debounce before pushing
    sign: true
    sign_with: maintainer-key

What it does:

  1. Watches src/ and docs/ with inotify / fswatch / FSEvents.
  2. Filters out editor swap files, temp files, and ignored patterns.
  3. Resets a 5-minute debounce timer on every edit.
  4. When the timer fires: runs pre-commit hooks, fails loudly on error.
  5. Generates a commit message: auto: changes in src/foo.py, src/bar.py.
  6. Creates a signed commit, optionally pushes after another debounce.
Why this is a feature, not a cop-out. Manual commits are great for big logical changes. Auto-commits are great for "I just edited a few files and want a checkpoint before I go get coffee." The point is not to replace intentional commits; it's to capture work-in-progress without forcing the developer to context-switch. The commits are still signed and the messages still tell you what changed.

Other daemon duties

  • Content-addressed cache — keeps a local CAS of every object the project has touched, for fast re-sync and offline operation.
  • Mirror sync — pushes/pulls partial mirrors on a schedule or in response to upstream events.
  • Peer serving — answers k33p get <hash> from other hosts on the same network. Optional; opt-in per project.
  • Auto-rollback — if a newly-pulled artifact fails its verification, the daemon can roll back to the last known-good pointer value.
  • Daemon-off mode — for users who don't want a background process. k33p sync does the same work on-demand.

🔐 Content addressing & trust

Everything in the store is content-addressed. That's not stylistic; it's load-bearing for the trust model.

The k33p hash

Every object has a multi-hash identifier:

k33p:sha256:abc123...
k33p:blake3:def456...
k33p:cidv1:bafy...       # CIDv1 compatible, for interop with IPFS / OCI

The hash is the identity. A k33p hash is a self-validating reference: if you have the bytes, you can verify them locally; you don't have to trust whoever gave them to you.

Trustless mirrors

Because every object is content-addressed, mirrors are inherently trustless:

  • A mirror serves content by hash. The client verifies the hash after download.
  • A mirror can lie about which hashes it has; it cannot lie about the content of any hash it returns.
  • Partial mirrors are first-class — a mirror with 80% of the objects is still useful for the 80% it has.
  • Mirrors don't need to be trusted; they need to be available. A peer on a LAN, a USB stick on a plane, an IPFS gateway, a corporate cache — all are interchangeable from the client's perspective.

IPFS-like caching, but typed

k33p is to content addressing what git is to git objects: same idea, different scope. Where IPFS addresses arbitrary content by content hash, k33p addresses typed project objects by content hash. A k33p hash knows its type (blob, commit, manifest, secret, artifact, pointer) and its channel. That makes the cache smarter: you can ask "give me all artifacts for coolproject" or "give me all secrets encrypted to maintainers@acme.com" and the cache can answer from metadata without re-downloading anything.

Pulling by hash, not by URL

# pull a specific object by its k33p hash
$ k33p get k33p:blake3:7a3f...

# pull from any peer that has it
$ k33p get k33p:blake3:7a3f... --from /media/usb/peer
$ k33p get k33p:blake3:7a3f... --from ipfs://bafy...
$ k33p get k33p:blake3:7a3f... --from https://cache.acme.com

URLs are still useful (for discovery, for transports with access control) but the canonical reference is a hash.

🚚 Smart transport & storage

Content addressing enables a handful of optimizations that fall out for free.

Deduplication

The store is a single CAS. The same blob — a dependency tarball used in two projects, a generated doc shared by source and artifacts, a secret encrypted with the same recipient set — is stored once. For multi-project orgs, this saves real disk space.

Compression

Per-object compression by content type:

  • Text (src, deps manifests, build logs): zstd or brotli.
  • Binaries (artifacts): stored uncompressed or with a smart codec (e.g., zstd for binaries that compress, passthrough for already-compressed images).
  • Encrypted blobs (secrets): already incompressible; stored as-is.

Delta transfers

Source channel uses rsync-style delta transfers against the CAS — transfer only the missing objects, in compressed form. The content hashes make delta computation trivial: "send me every object in src@v1.2.3 that I don't already have."

Sparse materialization

A role view defines what's on disk. A developer view materializes src + deps; a user view materializes artifacts. The store has the rest, but the working tree is sparse. This is the central win of views: the same project supports arbitrarily different materializations.

Parallel pipelined transfer

Large projects (e.g., fetching a 5 GB dep tree) transfer in parallel with priority for high-priority refs (the lock-pinned refs come first, then background refs).

🏢 Multi-tenancy

An org owns projects. Teams within the org have their own channels, their own permissions, and can themselves have sub-teams. The tree can go as deep as you want.

The URL scheme

k33p://acme/                              # the org
k33p://acme/backend/                      # a team
k33p://acme/backend/api/                  # a sub-team
k33p://acme/backend/api/coolproject       # a project owned by the sub-team
k33p://acme/backend/api/coolproject@v1.2.3  # a specific ref
k33p://acme/backend/api/megarepo/powder_play   # a subproject of a monorepo
k33p://acme/backend/api/megarepo/powder_play@v1.2.3  # at a tag

Org manifest

# k33p-org.yaml at the org root
org: acme
teams:
  backend:
    teams: [api, db, infra]
    projects: [coolproject, otherproject]
  frontend:
    teams: [web, mobile]
    projects: [coolproject-ui]
  sre:
    teams: []
    projects: [all]      # SRE can deploy anything

permissions:
  inherit: true          # child teams inherit parent permissions
  backend/api/coolproject:
    channels:
      src:     { read: true,  write: true  }
      private: { read: true,  write: true  }
      deps:    { read: true,  write: false }
      artifacts: { read: true, write: true }
      live:    { read: true,  write: [release-key] }
  backend/db/coolproject:
    channels:
      deps: { read: true, write: false }   # db team can read but not change deps

Why this matters

  • One URL, deep hierarchy. You can address any project at any level of the org tree without needing to know the full path upfront.
  • Permission cascade. A team inherits its parent's permissions unless it overrides. sre:projects: [all] is a real thing — SRE can deploy any project in the org.
  • Per-team private channels. The backend/api sub-team can have a private channel that only that sub-team sees. The parent team can't decrypt it.
  • Cross-team collaboration via shared channels. coolproject's deps channel might be readable by both backend/api and backend/db; the private channel is backend/api-only.

🛰️ Federation

Each channel has a single source of truth (the primary) and zero or more read-only mirrors. Just like git remotes, but for channels.

channels:
  src:
    type: source
    primary: git+https://github.com/coolproject/coolproject
    mirrors:
      - git+https://gitlab.com/coolproject/coolproject
      - git+ssh://mirror.acme.com/coolproject
      - ipfs://bafy...            # content-addressed mirror

How it works:

  • Fetch tries the primary first, then mirrors in order, in parallel.
  • Verify happens locally via content hashes — a mirror can't lie about the content of an object it returns.
  • Push goes to the primary only. Mirrors are read-only.
  • Promotion: a CI runner that builds on gitlab.com can publish a build manifest to the primary via a signed release key, even though the source mirror is on gitlab.
The mirror is a subset of content-addressed objects. A mirror with 80% of the objects is useful for the 80% it has. A mirror on a USB stick is useful on the plane. A mirror on a corporate cache is useful behind a firewall. No semantic difference from the primary for any object the mirror has.

🚜 Migration tools

The best version control system in the world is useless if you can't get your existing project into it. Migration is a first-class concern.

From git

# wrap an existing git repo
$ k33p import --from-git https://github.com/me/myproject
  → reads .git/, generates k33p.yaml
  → src channel = the existing git repo
  → no rewrite of git history (preserves SHAs)
  → existing CI / tooling keep working

From a tarball

$ k33p import --from-tarball ./snapshot.tar.gz --sign-with release-key
  → treats the tarball as a src channel snapshot
  → optionally signs the import

From an OCI image

$ k33p import --from-oci ghcr.io/me/myproject:v1.2.3
  → treats the image layers as artifacts
  → generates a build manifest claiming the original image as input
  → useful for "I have an OCI image but no idea how it was built"

Split a monorepo

$ k33p split --from megarepo --prefix active/games/powder_play
  → creates a new project: powder_play
  → src channel = the prefix's git history (history-preserving)
  → other prefixes become separate projects
  → shared deps become a deps channel
  → the k33p.yaml is generated; you review and commit

Convert to other formats

$ k33p convert --to oci-image           # build an OCI image from artifacts
$ k33p convert --to npm-package         # build an npm package
$ k33p convert --to cargo-crate         # build a Cargo crate
$ k33p convert --to flat-dir            # just the working tree

Migration playbooks

Common scenarios the migration tools should handle end-to-end:

  • "I have a git repo with a .env.example." → k33p import --from-git, then move real secrets to the private channel.
  • "I have a monorepo I want to split." → k33p split --prefix ... per project, review the generated k33p.yaml files, commit.
  • "I have an OCI image but no source." → k33p import --from-oci gives you an artifacts channel with provenance; the missing source is recorded as a known gap.
  • "I have a Cargo project and want to publish a binary." → k33p init --from-git, add an artifacts channel, configure the build manifest, done.
  • "I have a private fork I want to share with one other team." → Create a sub-team, grant access, share the project URL. No repo-per-team, no fork-and-pr workflow.

🔌 Compatibility with git

k33p doesn't replace git for the source channel. It wraps it. This is the single most important decision in the design: migration cost has to be near-zero or no one will adopt it.

  • k33p init --from-git <url> wraps an existing git repo. The .git/ directory is unchanged.
  • k33p git <args...> passes through to git for the source channel. All existing muscle memory works.
  • k33p.yaml is just a file in the repo. Committed, reviewed, signed — like any other file.
  • Existing CI (GitHub Actions, GitLab CI, Buildkite) keeps working. The CI's role is ci; it does k33p sync instead of git pull, and the rest is unchanged.
  • Existing tooling that reads .git/ directly (IDEs, blame tools, merge drivers) keeps working. k33p is a layer above, not a replacement.
  • Git's own object store is referenced from the k33p CAS by hash. Nothing is duplicated on disk.

You adopt k33p one channel at a time:

  1. Add k33p.yaml to your repo. src is git, just declared.
  2. Add an artifacts channel. Push your release binaries as OCI objects with signed manifests.
  3. Add a deps channel. Vendoring becomes a k33p concern, not a custom CI script.
  4. Add a private channel. Secrets stop living in .env checked into a Slack thread.
  5. Add a live channel when you want a latest pointer that moves under your control instead of whoever last tagged.
  6. Add a daemon config when you're tired of typing git commit -am ....
  7. Move into an org when you have more than one project and want shared permissions.

At every step, the project is more k33p and less of a glue job. You stop wherever you stop. There's no "v2 migration" cliff.

🗂️ Project layout

The on-disk layout is role-dependent. There is no required channel layout. The only canonical things on disk are the CAS and the manifest.

coolproject/                          # project root
├── k33p.yaml                         # project manifest (committed to src)
├── k33p.lock                         # cross-channel lock (with toolchain)
├── README.md
├── .git/                             # src channel — git's own object store
├── .k33p/                            # k33p state (gitignored)
│   ├── store/                        # content-addressed object store (CAS)
│   │   ├── 12/abcdef...              # git-like sharded layout
│   │   ├── 34/...
│   │   └── ...
│   ├── state/                        # daemon state (last auto-commit, etc.)
│   └── cache/                        # transient daemon cache
└── (working tree at root — view-dependent)
    # for the developer view:
    #   src @ ./
    #   deps @ ./node_modules
    # for the maintainer view:
    #   src @ ./
    #   private @ ./.env
    #   artifacts @ ./build/
    # for the ci view:
    #   src @ ./
    #   deps @ ./.k33p/vendored/
    #   private @ (env-mount, no on-disk)
    #   artifacts @ ./build/
    # for the end-user view:
    #   artifacts @ ~/.local/bin/  (install)

Three properties to notice:

  1. The store is shared. The same blob — used in src and artifacts, say — lives in the store once. No duplication across channels.
  2. The working tree is computed. There is no .k33p/private/ or .k33p/deps/ by default. A view decides where channel content materializes, and the materialization can be hardlinks (cheap), copies, or mounts.
  3. The lockfile carries toolchain info. A reproducible build requires the compiler, build system, and codegen options to be pinned. k33p.lock records them.

🛡️ Security model

ThreatMitigation
Secret leakage in public repo Impossible by construction. Secrets live in an encrypted channel, not a file in the source tree.
Dependency confusion attack Dependencies pinned by content hash; lockfile is signed; resolution is reproducible.
Backdoored artifact Re-build from signed source + deps + toolchain; the manifest claims specific inputs, the build can verify them.
"It works on my machine" The lockfile pins compiler, build system, linker, codegen, and env hash. Reproducible builds by default.
Stolen credentials Hardware-backed keys (age + YubiKey, SSH agent, OS keychain); audit log of every decryption.
Rogue maintainer moving latest Pointer moves in the live channel are signed, rate-limited, and auditable. The audit log is itself immutable.
Rogue maintainer rewriting history History rewriting is impossible in the typed channels; the live channel can only add pointer updates, not delete old ones (unless retention is explicitly configured).
Compromised mirror Content addressing + signatures. A mirror is a subset of signed objects; partial corruption is detectable. No need to trust the mirror — verify the hash.
Replay of old manifest Lockfile is signed; verifying a manifest against the current lock is a strict operation.
Cross-team secret leak Each team has its own private channel; encryption is per-recipient; a parent's key cannot decrypt a child's private channel.

The most important property: the secret channel is structurally incompatible with the public channel. You cannot accidentally put a secret in source, because secrets don't have paths in source. The most common class of breach in modern projects becomes a type error.

  → powder_play-scoped artifacts channel becomes the new project's artifacts
  → new project's k33p.yaml is generated; you review
  → a "moved-to" pointer is added to the monorepo's live channel:
      "moved: powder_play → https://github.com/calvinloveland/powder_play"
$ # clone the new standalone project
$ k33p clone https://github.com/calvinloveland/powder_play
  → src is now a standalone git repo (not a path-scoped slice)
  → channels follow the subproject
  → no breakage for existing consumers

❓ Open questions

The design decisions I haven't made yet. Calling them out so the design can be critiqued on its weakest joints.

What does the k33p hash look like? Multi-hash (sha256/blake3/cidv1) is the answer, but the canonical encoding format isn't pinned. k33p:blake3:7a3f... vs bafy... vs a custom base — the choice has interop implications with IPFS, OCI, and content-addressed mirrors.
How do views compose? A view can extends another, but composition order matters (override vs. append). Are views a merge-join, a layered stack, or something more like CSS specificity? A few edge cases will force a decision.
How does a multi-primary org work? Right now each channel has one primary. An org with multiple regions might want geo-distributed primaries. A cross-region merge protocol? CRDTs? Or just "one primary, many mirrors" with eventual consistency?
Live channel ownership. Who can move latest-stable? A single key, a multi-sig threshold, an org-wide role? The update_policy field exists, but the governance model isn't fully specified.
Daemon protocol. The daemon speaks some protocol to the rest of k33p (events, hooks, status). Is it a Unix socket? An HTTP API? A CRDT-based pub/sub? I lean toward a simple HTTP API on localhost:0 with structured events, but the surface is still TBD.
Pointer update retention. The live channel's history: ring(50) is a default. For audit-heavy orgs, you might want history: full (every pointer update ever recorded). For high-traffic canary pointers, you might want history: ring(5). The right default per pointer type is a v1 design exercise.
Lock vs. tag (resolved). A maintainer says "v1.2.3" — that's a tag (human-friendly, signed, points to a ref). A CI runner says "v1.2.3" — that's a lock entry (machine- readable, pins every channel). The relationship: a tag points to a lock; the lock pins the ref set. Same model as git tags pointing to commits, but for the whole project.
What does "trustless mirror" mean for build reproducibility? A mirror can serve the source commit and the dep lock by hash, but the toolchain (rustc 1.79.0) is a binary; you have to trust whoever built the toolchain image. Container digests help, but the supply chain for compilers is its own problem. Out of scope for k33p to solve, but worth calling out.
How do nested subprojects work? Right now a subproject lives at a path, but does it own its own sub-subprojects? Probably not by default — a subproject is a leaf, and the path hierarchy is a flat namespace. But a "monorepo of monorepos" pattern (where megarepo is itself a subproject of calvinloveland/megarepo-of-megarepos) would benefit from one level of nesting. The right design here is unclear.
Subproject name vs path disambiguation. A subproject can be addressed by short name (powder_play) or full path (active/games/powder_play). When the short name collides across nested paths, the resolver has to pick. My current instinct: short names are unique within a monorepo (the manifest enforces this); full paths are always unique. If you want to use the same short name in two paths, you have to rename one.
Subproject renaming and history rewriting. Git doesn't track renames (it tracks content similarity). When a subproject moves or renames, do we expose that as a separate moved-to pointer in the live channel? Or do we let git's content-tracking do its thing? The pointer approach is more explicit and auditable; the content-tracking approach is more automatic. I lean toward the pointer approach for explicit moves, with content-tracking as a fallback for unscripted renames.
How are subproject shared deps shared, exactly? The shared-deps pattern is described above, but the actual mechanism isn't pinned. Option A: a shared-deps subproject that other subprojects reference through their artifacts channel. Option B: a monorepo-level "shared deps cache" that's referenced by hash. Option C: just dedup across the CAS and let consumers pick which copy. Each has tradeoffs; a v0.2 design exercise will pick one.
Subproject visibility. A monorepo can have public subprojects (e.g., a docs site) and private subprojects (e.g., an internal admin tool) at the same time. The visibility declaration lives in the subproject's manifest entry. Open question: can a private subproject share a channel with a public one? Probably not without explicit expose_to declarations; the default is isolation.

🔤 Why "k33p"

  • keep — keep your code, keep your secrets, keep your builds, keep your history, keep it reproducible.
  • 33 — three threes, or "eee" — keep everything. The digits are playful, not pretentious.
  • Four characters — same shape as git, hg, svn. CLI-friendly. Stands out from a list of long names.
  • Lowercased — like a tool, not a brand. A verb that happens to be a noun.
  • Spellable on a phone — important for typing into a terminal over a remote shell.

k33p design draft v0.3 — incorporates feedback from v0.2 review: monorepos are now the first-class citizen. A k33p project is a monorepo with one or more subprojects; a "single project" is a degenerate monorepo with one subproject at the root path. Subprojects have their own k33p.yaml (or inherit the parent's), their own view, their own channel subscriptions, and their own lockfile. The other channels (private, deps, artifacts) are scoped to each subproject via a scope: key, so a secret for powder_play is a different secret than one for full_auto_ci — even though they live in the same monorepo. Path-scoped sub-clones (k33p clone monorepo/sub) materialize only the subproject's slice. Cross-subproject references go through signed artifacts (the shared-ui-library pattern), not raw source. k33p split and k33p merge convert between subprojects and standalone projects without rewriting git history.

v0.2 additions: content-addressed store + per-role views replace the required on-disk layout; the k33p daemon auto-commits with debounce; the live channel formalizes mutable pointers with signed, rate-limited, auditable updates; org/team multi-tenancy; IPFS-like trustless mirrors; toolchain pinned in the lockfile; smart transport with compression and dedup; comprehensive migration tools.

The most important property of this design is what it makes impossible: accidentally committing a secret to a public repo, publishing an unsigned artifact, downloading 1.2 GB of git history just to run a binary, moving a latest pointer without an audit trail, rebuilding a project on a different compiler, or accidentally pulling 49 subprojects' worth of code when you only wanted one. The type system, the content hash, the path scope, and the daemon — not the honor system.
