🔧 Hardware Validation Plan

Which simulator assumptions need real ESP32 hardware to falsify, and a phased testing schedule to do it. This is the bridge between the browser-based algorithm work and a living-room full of self-deploying surround speakers.

Why hardware testing?

The simulator proves the algorithms work in an idealized world: perfect TOA estimators, a shared global clock, no I2S peripheral conflicts, and acoustic propagation that obeys the image-source model exactly. Real ESP32 hardware violates every one of these to some degree. The question is how much — and whether the joint LM solver and the various hardening knobs (robust, earliest-peak, shot averaging) can absorb the real-world errors.

🔴 Single biggest hardware risk: The ESP32 has two independent I2S controllers (I2S0 and I2S1). If the MAX98357A speaker DAC runs on one and the INMP441 microphone on the other, their bit clocks are generated by independent PLLs. The matched-filter TOA estimator assumes playback and capture share a sample clock; if they free-run with even ±50 ppm mismatch, the chirp duration drifts between TX and RX and the correlation peak smears. This project's first hardware test must answer: do we need a shared BCLK wire, or can the two I2S controllers be disciplined to the same clock reference?

The table below maps every simulator assumption to the hardware test that will validate or falsify it, organized by risk tier. The testing schedule groups these into five phases you can execute with a soldering iron, a laptop, and a tape measure.

All assumptions requiring hardware validation

#1 🔴 Tier 1 — project-killer potential
I2S clock domains are coherent between DAC and mic
Baked in: capture.mjs — shared sampleRateHz: 48000 for playback and capture; one shared clock domain is assumed silently.
ESP32 has two I2S controllers. The typical pinout (MAX98357A on I2S0, INMP441 on I2S1) means two independent bit clocks. A ±50 ppm mismatch causes the chirp to stretch/shrink between TX and RX, degrading the cross-correlation. If they can't share a clock reference, the TOA estimate carries an extra unknown scaling that the solver doesn't model.
✅ Test: Phase 0 — probe both BCLK pins with a scope; compare frequencies. Phase 1A — loopback a known chirp and measure the recovered duration vs. transmitted duration.
#2 🔴 Tier 1 — project-killer potential
Self-path delay is stable and calibratable
Baked in: world.mjs makeNode() — selfPath: SELF_PATH (a small fixed constant per node). The solver uses self-arrivals to anchor each node's clock offset.
Each node hears its own speaker through a short air path + PCB crosstalk + cabinet resonance. This delay is neither a known constant nor necessarily stable — it may drift with temperature, supply voltage, and volume setting. If it varies by more than a few µs between calibration runs, the clock offset estimate inherits that error for all other nodes.
✅ Test: Phase 1B — 100 repeated loopback captures at each of several volume/temperature points. Measure the self-path TOA mean and std dev. If std dev > 5 µs, the anchor is unreliable and needs a different strategy (e.g., a wired sync pulse).
#3 🔴 Tier 1 — project-killer potential
Matched-filter cross-correlation runs fast enough on ESP32
Baked in: dsp.mjs — pure JS chirp + correlation + parabolic peak fit. Port map says "MCU-friendly optimizations needed."
A 48 kHz, ~96-sample chirp cross-correlated against a full capture window (thousands of samples) is ~10⁶ multiply-accumulates per pair × n² pairs. The Xtensa LX6 has no hardware FPU — integer-only, 240 MHz. If one TOA estimate takes tens of ms, the full n² sweep takes seconds, blowing the calibration phase budget and potentially causing clock-drift contamination across the sweep.
✅ Test: Phase 0/1 — port the cross-correlation to fixed-point C, run esp_array_capture_and_estimate() on one capture, measure wall-clock with esp_timer_get_time(). If >50 ms per pair at 8 nodes → ~3 seconds for all pairs → risky.
#4 🔴 Tier 1 — project-killer potential
ESP32 can timestamp TOA with ~20 µs precision
Baked in: world.mjs — micJitterSec: 2e-5 (20 µs ≈ 7 mm). dsp.mjs uses sub-sample parabolic peak refinement.
The simulator assumes TOA jitter is 20 µs (roughly one 48 kHz sample). But the ESP32's I2S driver reports buffer-done interrupts, not first-sample timestamps. The delay between the actual sample clock edge and the CPU servicing the interrupt depends on FreeRTOS scheduling, cache misses, and Wi-Fi activity — all jitter sources the simulator doesn't model.
✅ Test: Phase 1A — 1000 loopback chirps. Measure the std dev of the recovered TOA. If it's >100 µs, sub-sample refinement is wasted and the solver's jitter floor is 3+ cm.
#5 🟡 Tier 2 — high impact, likely diverges
Sample rate mismatch between DAC and mic is negligible
Baked in: calibration-config.mjs — DEFAULT_CALIBRATION_CHIRP_OPTIONS.sampleRateHz: 48000 shared.
Even with disciplined PLLs, two I2S controllers may have a small systematic rate offset (internal PLL accuracy, external crystal tolerance). A 0.01% mismatch over a 2 ms chirp = 0.2 samples of drift — negligible. A 1% mismatch (= one controller in 44.1 kHz mode accidentally?) would destroy the correlation.
✅ Test: Phase 0 — verify both I2S controllers are configured for 48 kHz with the same clock source if possible (I2S0 master, I2S1 slave to same BCLK).
#6 🟡 Tier 2 — high impact, likely diverges
WiFi clock sync leaves ≤±100 µs residual with stable skew
Baked in: world.mjs — clockOffsetSec: ±1e-4 range, clockSkew: ±50 ppm max.
The simulator generously assumes a tight WiFi sync. Real ESP32 NTP or beacon-timestamp sync depends on AP timing, interrupt latency under Wi-Fi load, and FreeRTOS scheduling. Residual offsets could be ms-level, not µs-level, especially on a congested 2.4 GHz band. The joint LM solver can estimate offsets, but large residuals demand more multistart iterations or fail to converge.
✅ Test: Phase 2A — build two nodes, have each send a timestamped WiFi packet when it starts its chirp. Measure the actual offset scatter across 100 trials in a typical home Wi-Fi environment.
#7 🟡 Tier 2 — high impact, likely diverges
Chirp audible range and volume work for real rooms
Baked in: calibration-config.mjs — 3–8 kHz linear chirp, 2 ms, Hann-windowed. INMP441 sensitivity –26 dBFS. MAX98357A 3W output.
The chirp dBFS/m relationship is uncalibrated. The INMP441 might clip at close range (loud chirp, speaker 10 cm from mic) or the SNR might be too low at 5 m range in a noisy room. Small speakers may have poor response above 6 kHz, cutting the effective chirp bandwidth. The matched-filter processing gain helps, but a 10 dB SNR loss at the extremes could break localization.
✅ Test: Phase 1A and Phase 3A — capture raw waveforms at 0.5 m, 1 m, 2 m, 4 m in a quiet room and a typical living room. Compute actual SNR of the matched filter peak.
#8 🟡 Tier 2 — high impact, likely diverges
Speaker→mic feedback doesn't cause oscillation or saturation
Not modeled in simulation — one-way propagation only.
With 6–8 nodes in a room, each one plays a chirp while its own mic is listening. Acoustic feedback (own speaker into own mic) could saturate the INMP441 preamp or cause howling at high gain. The simulator's self-path is a ~2 cm delay with fixed attenuation; real acoustic coupling includes cabinet resonance, direct mechanical vibration through the breadboard/PCB, and room reflections returning to the same mic.
✅ Test: Phase 1A — capture while playing at increasing volumes. Check for clipping (sample values at ±1.0) or spectral contamination in the silence between chirps.
#9 🟡 Tier 2 — high impact, likely diverges
0.3 s gap between emissions is enough for reverb decay
Baked in: calibration-config.mjs — gapSec: 0.3.
The simulator's image-source model assumes a simple reverb tail. A real living room with hard floors, windows, and furniture can have RT60 > 0.5 s at certain frequencies. Late echoes from emission N could overlap with emission N+1, adding false peaks to the cross-correlation that earliest-peak can't distinguish from the true direct arrival.
✅ Test: Phase 3A — record the full sweep in an untreated room. Inspect the intersignal gap for residual energy from the previous chirp. If >5% of peak amplitude persists, increase gapSec or implement adaptive silence detection.
#10 🟠 Tier 3 — important, mitigatable
Mesh gossip completes before clock state goes stale
Baked in: mesh.mjs, firmware-protocol.mjs — n·(n−1) broadcasts per node.
ESP-NOW or ESP-MESH broadcast latency depends on channel congestion, retransmissions, and node count. If a full gossip round takes minutes, the clocks have drifted beyond the solver's skew model. The simulator assumes gossip is effectively instantaneous.
✅ Test: Phase 3B — measure end-to-end gossip time for 4, 6, 8 nodes. If >60 s, the solver needs a fresher clock-sync step before solving, or the gossip protocol needs optimization.
#11 🟠 Tier 3 — important, mitigatable
Per-node self-path calibration is stable across reboots
Baked in: demo/index.html assumes same binary on all nodes; per-node constants not yet in NVS.
Each node's self-path delay (speaker→mic) needs to be measured once and stored. If it drifts with temperature or voltage, the stored value becomes wrong. The simulator assumes a single fixed constant.
✅ Test: Phase 1B — measure self-path TOA across 10 power cycles and 10°C temperature variation. If >10 µs variation, implement periodic self-calibration or use a wired reference.
#12 🟠 Tier 3 — important, mitigatable
LM solver runs acceptably on ESP32 coordinator node
Baked in: bench.mjs — ~640 ms for 12 nodes on x86_64.
The benchmark runs on a 3 GHz x86_64 with hardware FPU. Porting the LM solver (matrix operations, SVD, Jacobian) to a 240 MHz Xtensa without FPU means software-emulated double-precision or careful fixed-point. Expect 10–50× slowdown → 6–30 seconds for 12 nodes. This might be acceptable for a one-time calibration but not for repeated recalibration.
✅ Test: Phase 3C — port the solver to ESP32 (or use a subset for validation). Measure wall-clock time for 4, 6, 8 nodes. If >60 s for 8 nodes, consider offloading solve to a phone/PC via Bluetooth or WiFi.
#13 🟠 Tier 3 — important, mitigatable
5.1 audio input path works (Bluetooth A2DP / USB / line-in)
Baked in: demo/index.html — mentions Bluetooth A2DP, USB audio, line-in as possibilities.
None of these are trivial on ESP32. Bluetooth A2DP adds 150–300 ms latency (fine for movies, bad for live performance). USB audio requires the USB OTG peripheral and a separate USB audio class driver. Line-in requires an ADC or an I2S ADC codec. The best path depends on the use case and hasn't been validated.
✅ Test: Phase 4 — implement one input path, measure end-to-end latency from source to speaker output. If >500 ms total, the system feels laggy for any interactive use.
#14 🟠 Tier 3 — important, mitigatable
Sweet-spot listening position is known or reasonably assumed
Baked in: surround.mjs, render.mjs — compensation targets a specific sweet spot (default center of room).
The panner compensates delay and gain for one listening position. If the listener moves 1 m off-center, the compensation becomes misaligned — the time-of-arrival alignment assumes the sweet spot. The simulator doesn't (yet) model off-axis degradation.
✅ Test: Phase 4 — measure impulse concentration at 0.5 m and 1 m offsets from sweet spot. If concentration drops below 0.7 at 0.5 m, the system needs either a wider sweet spot or listener tracking.
#15 🔵 Tier 4 — low risk, nice to validate
Nodes don't move during calibration sweep (~2 s)
Implicit in one-shot capture model.
Real furniture might get bumped. But a 2 s sweep is short enough that this is very unlikely to matter.
✅ Quick check during Phase 3 — bump a node mid-sweep; does the solver detect the inconsistency via high residuals?
#16 🔵 Tier 4 — low risk, nice to validate
Chirp is subjectively non-intrusive
2 ms chirp, 3–8 kHz sweep at moderate volume.
The chirp sounds like a short "chirp" — some people may find it annoying. The sweep happens once at setup, so probably acceptable.
✅ Subjective: play the chirp for a few people, ask if they'd tolerate it during a one-time calibration.
#17 🔵 Tier 4 — low risk, nice to validate
Small speaker reproduces 3–8 kHz chirp adequately
Implicit — small 2–3" speaker assumed.
Cheap small speakers often roll off above 6–8 kHz. The upper half of the chirp may be 10–20 dB quieter, reducing effective bandwidth and degrading TOA precision.
✅ Phase 1A — record the chirp with a calibrated reference mic (or phone mic as a relative check). Compare spectrum at 0.5 m vs. the chirp template.
#18 🔵 Tier 4 — low risk, nice to validate
Room temperature (speed of sound) is constant during calibration
Baked in: acoustics.mjs — constant SPEED_OF_SOUND.
Speed of sound changes ~0.6 m/s/°C. A 5°C drift during a 2 s sweep would change the apparent distance by ~0.01% — negligible. The solver wouldn't notice.
✅ Easy to check with a temp sensor. No action needed unless the system is used outdoors or near heat sources.
#19 🔵 Tier 4 — low risk, nice to validate
All nodes can coordinate a simultaneous calibration start
Implicit — firmware session state machine starts at boot.
The coordinator model broadcasts a "go" signal. WiFi broadcast latency (~1–10 ms) is small relative to the 100 ms first-emission offset. Low risk.
✅ Phase 2 — measure the spread of "go" arrival times across nodes. If >50 ms, adjust firstEmitSec.

Testing schedule

Five phases, ordered by dependency. Each phase builds on the previous. You need one soldering iron, an oscilloscope (or logic analyzer), a tape measure, and a laptop. Total elapsed time for a hobbyist: roughly 2–4 weeks of evenings/weekends if parts are on hand.

Phase Name Assumptions tested Hardware needed Duration
0 Single-node bring-up #1, #3, #5 1 node, scope 1 day
1 Loopback accuracy #1, #2, #4, #7, #8, #17 1 node, tape measure 2–3 days
2 Two-node clock sync + ranging #6, #9, #19 2 nodes, tape measure 2–3 days
3 Multi-node mesh calibration #9, #10, #11, #12, #15 4–8 nodes 5–7 days
4 Surround audio playback #13, #14 4–8 nodes, audio source 3–5 days

Phase 0 — Single-node bring-up

⏱ ~1 day 🔧 1 node, oscilloscope 🎯 Goal: verify the hardware boots, I2S peripherals initialize, and the two I2S controllers' clock relationship is understood.
Before this phase, you should have built one node per the assembly guide and run idf.py build flash monitor to see the boot messages.
  1. Verify I2S DAC output. Flash the firmware, call esp_array_play_chirp(). Probe the MAX98357A's BCLK pin with a scope. Confirm 48 kHz × 32 bits × 2 channels = ~3.072 MHz. Listen for an audible chirp from the speaker.
  2. Verify I2S mic capture. Call esp_array_capture_and_estimate() while playing a continuous tone. Print the first 100 raw samples over serial. They should show a periodic waveform, not all zeros or clipping.
  3. Scope both I2S BCLK pins simultaneously. Probe GPIO 26 (MAX98357A BCLK) and GPIO 19 (INMP441 SCK) on a dual-channel scope. Measure their frequencies and phase relationship.
    🔶 Pass condition: Both BCLKs measure 48 kHz frame rate (3.072 MHz for 32-bit I2S) within ±10 ppm of each other. If they differ by more, this is the project's first design decision: either wire a shared BCLK (route one controller's clock output to the other's clock input), or design a clock-domain-crossing calibration step.
  4. Benchmark the matched-filter cross-correlation. Capture one chirp, run esp_array_capture_and_estimate() in a loop of 100 iterations, time with esp_timer_get_time(). Report mean ± std dev.
    🔶 Pass condition: Mean < 50 ms per pairwise TOA estimate. (At 8 nodes × 8 listeners = 64 pairs → < 3.2 s total). If > 200 ms, the optimizer in dsp.mjs needs fixed-point or reduced chirp length before multi-node testing.
✅ Phase 0 done when: Both I2S controllers produce valid clocks at 48 kHz, the chirp is audible and capturable, and the cross-correlation C implementation runs in acceptable time.

Phase 1 — Loopback accuracy

⏱ 2–3 days 🔧 1 node, tape measure, quiet room 🎯 Goal: quantify the TOA estimation variance, self-path stability, and acoustic coupling on a single node.
Sub-phases 1A (free-field accuracy) and 1B (self-path stability). Do 1A first, then 1B.

1A — Free-field TOA accuracy

  1. Place the speaker 1.00 m from the mic (use a tape measure). Ensure both are at the same height, clear of reflecting surfaces.
  2. Run 100 chirp-capture cycles. For each, measure: TOA = estimateTOA(capture, chirp, 48000). The true propagation delay is 1.00 m / 343 m/s ≈ 2.915 ms. Compute the error: TOA − 2.915 ms.
  3. Report statistics: mean error (bias), standard deviation (jitter), p95 absolute error. If the I2S clock-domain issue exists, expect a systematic bias or periodic error pattern.
  4. Repeat at distances: 0.5 m, 2.0 m, 4.0 m. The 4 m case tests whether the chirp is loud enough for good SNR at the far end of a typical room.
  5. Repeat with earliest-peak vs. strongest-peak modes (the estimatorMode option). Add a reflective surface (e.g., a clipboard) near the mic to create a deliberate echo. Verify that earliest-peak rejects it while strongest-peak gets biased.
✅ Pass condition (1A): Bias < 5 mm equivalent, std dev < 10 mm equivalent at all distances up to 4 m. Earliest-peak correctly rejects close echoes.

1B — Self-path stability

  1. Capture the self-path 100 times (node plays, its own mic listens). The self-path is typically a few cm — measure the mean TOA and convert to distance.
  2. Repeat at 3 volume levels (low, medium, high via MAX98357A gain). Does the self-path delay change? (Speaker excursion, cabinet resonance).
  3. Power-cycle the node 10 times. After each reboot, measure the self-path. Report stability across reboots.
  4. If available: heat the node with a hair dryer to ~40°C, cool to ~15°C. Measure self-path at each extreme. The speed of sound changes ~0.6 m/s/°C, but the path is so short (~2 cm) that temperature effects are tiny — the question is whether the electronics (DAC filter, ADC group delay) drift.
✅ Pass condition (1B): Self-path std dev < 5 µs across all conditions. If not, the self-path anchor is unreliable and the solver needs a different clock-offset reference (e.g., a wired sync pulse, or treating the self-path as an unknown the solver also estimates).

Phase 2 — Two-node clock sync + ranging

⏱ 2–3 days 🔧 2 nodes, tape measure, WiFi AP 🎯 Goal: validate the end-to-end acoustic ranging chain with a WiFi clock sync between two nodes.
This is the first test that exercises the distributed calibration flow: WiFi sync → chirp → capture → TOA → range. Two nodes are the minimal multi-node mesh.
  1. Implement a simple WiFi clock-sync protocol on both nodes: Node A broadcasts a timestamped "sync" packet; Node B records its local time on receipt. The offset is half the round-trip (or use a simple NTP-like exchange). This is the coarse sync the simulator assumes leaves ±100 µs residual.
    💡 For Phase 2, a one-way broadcast with known symmetric latency is sufficient. Don't optimize yet — just measure what you get.
  2. Place nodes 2.00 m apart in a quiet room. Run the calibration lifecycle: sync → plan → Node A chirp → both nodes capture → Node B chirp → both nodes capture.
  3. Compute the range from Node A's chirp as heard by Node B. The TOA on Node B's clock minus the sync-adjusted emission time gives the propagation delay. Convert to distance. Compare to the tape-measure 2.00 m.
  4. Repeat 50 times. Report mean ranging error and std dev. This isolates the combined error of: WiFi sync jitter + mic jitter + matched-filter TOA error.
  5. Repeat at 0.5 m, 1.0 m, 3.0 m, 5.0 m. Does the error grow with distance (SNR loss) or stay bounded?
  6. Introduce a controlled clock offset by delaying Node B's sync response by a known amount (use vTaskDelay(10 / portTICK_PERIOD_MS)). Verify the solver's joint estimation recovers the extra offset.
✅ Pass condition: Ranging error < 5 cm RMS at all distances up to 5 m. If error is large and uncorrelated with distance, the WiFi sync is the dominant error source. If error grows linearly with distance, the speed-of-sound assumption or I2S clock skew is wrong.

Phase 3 — Multi-node mesh calibration

⏱ 5–7 days 🔧 4–8 nodes, large room, tape measure 🎯 Goal: run the full distributed calibration pipeline on real hardware and compare recovered positions to ground truth.
Build all nodes, scatter them in a room, run the full firmware session state machine (sync → plan → capture → gossip → solve → ready). This is the first time the complete system runs outside the browser.

3A — Centralized calibration (one coordinator captures everything)

  1. Place 6 nodes in known positions in a room. Measure their exact coordinates with a tape measure (ground truth). Use a 6 m × 5 m area if possible. Mark positions on the floor with tape.
  2. Run the calibration sweep with all nodes emitting in round-robin and all nodes capturing. Collect all observations on one coordinator via serial or WiFi.
  3. Run the solver (same LM solver from localize.mjs, ported to C). Compare recovered positions to ground truth via Procrustes alignment.
    🔶 Expected: Large systematic errors if the I2S clock-domain issue (assumption #1) hasn't been resolved. If resolved, expect ~2–10 cm error depending on room acoustics.
  4. Repeat in 3 rooms: quiet office (carpet, low reverb), living room (hard furniture, moderate reverb), and an untreated room with hard walls (high reverb). The simulator predicts the high-reverb case will fail without earliest-peak + robust — this is the test of that prediction.

3B — Distributed gossip

  1. Implement the gossip protocol from mesh.mjs in C (ESP-NOW or ESP-MESH). Each node broadcasts its listener-row packet after the sweep. One coordinator collects all rows.
  2. Measure gossip latency for 4, 6, 8 nodes. Time from last chirp capture to coordinator having the full matrix.
  3. Test with intentional packet loss: drop random row packets on the coordinator side. Verify the robust LM solver degrades gracefully (the simulator predicts 30% loss at 8 nodes still localizes within ~15 cm).

3C — On-device solver benchmark

  1. Port and run the LM solver on one ESP32 (the coordinator). Time it for 4, 6, 8, and 12 nodes (12 might need simulated extra rows).
  2. If solve time exceeds 60 s for 8 nodes, consider these mitigations:
      • Reduce multistart count (try 2 instead of 8)
      • Offload to a PC/mobile via WiFi serial
      • Use a two-stage solver (coarse grid + local refinement)
✅ Phase 3 done when: 6 nodes localize with < 10 cm median error in a quiet room and < 20 cm in a reverberant room (with earliest-peak + robust enabled). Gossip completes in < 30 s for 8 nodes. The solver runs in < 30 s on the coordinator.

Phase 4 — Surround audio playback

⏱ 3–5 days 🔧 4–8 nodes, audio source 🎯 Goal: play real 5.1 audio through the self-localized array and measure channel separation at the sweet spot.
This is the payoff: once the mesh knows its geometry, pan 5.1 channels onto the discovered layout, apply per-speaker compensation, and verify the rendering quality.
  1. Implement the surround panner in C (port from surround.mjs). The coordinator computes per-speaker pan gains + delay compensation + gain compensation and sends each node its per-channel mix coefficients.
  2. Play a test tone per channel (the "Play test tone" button from the simulator, but on hardware). Walk around the sweet spot — verify that front-left sounds left, etc. Measure with a phone mic or SPL meter.
  3. Play 5.1 test content (a movie scene or test tone sequence). Evaluate subjectively: does the surround image feel correct? Are there audible artifacts (clicks, pops, delay smearing)?
  4. Measure sweet-spot width. Move 0.5 m left, right, forward, backward. At what offset does the phantom center image collapse or the left/right separation vanish? The simulator's render.mjs channelSeparation() function makes predictions about this — test them.
  5. End-to-end latency measurement. Feed a pulse through the entire chain: audio source → coordinator → panning → WiFi distribution → each node's DAC → speaker. Measure with a mic at the sweet spot. Total latency should be < 200 ms for video sync (if used with a TV) or < 50 ms for interactive use.
🟡 Important: Don't start Phase 4 until Phases 0–3 pass. If the localization is inaccurate, the panning will be wrong and you won't know whether the error is in the panner or the geometry. Isolate the localization first.
✅ Phase 4 done when: A listener at the sweet spot can correctly identify which virtual channel is playing (L, C, R, Ls, Rs). End-to-end latency < 200 ms. The system plays a full 5.1 audio source without audible artifacts.
🧪 Beyond Phase 4: Once the basic system works, the next tier of hardware experiments includes:
  • Node failure tolerance — kill one node mid-session; does the panner redistribute its channels?
  • Re-calibration drift — run calibration weekly; do the recovered positions drift with temperature/humidity?
  • Battery power — run on LiPo; does the I2S noise floor increase on battery vs USB?
  • Multiple sweet spots — precompute compensation for 2–3 listening positions and blend.
  • Over-the-air firmware updates — update all nodes from the coordinator.
