Connectivity-first provisioning

Bootable NixOS bootstrap image for remote-smart setup

The image should do one job exceptionally well: get a brand-new machine online quickly and safely so an already-configured Calnix machine can connect, inspect the hardware, choose the right host profile, and drive the install remotely.

Why this fits Calnix

The repo already has useful building blocks. The bootstrap image can reuse them in a thinner installer-focused profile.

Remote access

modules/remote-access.nix already enables SSH, Tailscale, and mosh-friendly firewall rules.

Networking

modules/desktop.nix already uses NetworkManager, which is a good base for Wi-Fi and Ethernet onboarding.

Host-aware flake

The repo is already organized around host-specific NixOS configurations, which makes a controller-driven install workflow natural.

Core design principles

The image should optimize for successful handoff rather than a polished local environment.

Outbound-first connectivity

New machines often sit behind NAT or unknown Wi-Fi. Prefer connectivity patterns where the machine dials out and becomes reachable.

No reusable secrets

The ISO may be copied widely, so it must not contain reusable Tailscale auth keys, private SSH keys, or long-lived host credentials.

Fast path for common cases

Wired DHCP should be zero-touch. Wi-Fi should be available through a small TUI flow without requiring a graphical desktop.

Remote-control friendly

The live image should expose enough machine state for the controller agent to understand disks, NICs, firmware mode, GPU, RAM, and other install-relevant facts.

Recoverable when fancy paths fail

There should always be a manual fallback for bad Wi-Fi, captive portals, or overlay-network trouble.

Proposed architecture

Keep intelligence centralized on the controller and keep the new machine thin.

1. Controller machine

  • Create one-time bootstrap credentials
  • Wait for the new machine to appear
  • Collect hardware facts remotely
  • Choose the host profile and install plan
  • Run the install and verify cutover

2. Bootstrap image

  • Bring up networking
  • Offer temporary authenticated remote access
  • Collect machine inventory
  • Hand off to remote install orchestration

3. Optional rendezvous layer

Prefer Tailscale or another outbound enrollment path. If that fails, support a reverse-tunnel fallback.

calnix bootstrap prepare
calnix bootstrap wait
calnix bootstrap install --target <bootstrap-host>

Connectivity plan

Layer the options from lowest friction to most defensive fallback.

Tier 0 · easiest path
Wired auto-connect
  • Start DHCP on Ethernet immediately
  • Advertise hostname on mDNS if available
  • Show current IPs on the console
  • Start the bootstrap agent automatically
Tier 1 · local onboarding
Wi-Fi via TUI
  • Use NetworkManager with nmtui or a small nmcli wrapper
  • Keep interaction local and minimal
  • Persist Wi-Fi only for the live session unless explicitly requested
Tier 2 · preferred remote path
Tailscale enrollment
  • Controller creates a single-use or short-lived auth key
  • User transfers the key by short code, QR, or removable media
  • Bootstrap image runs tailscale up with temporary or ephemeral enrollment
  • Controller waits for the node to appear and then SSHes into it
Tier 3 · outbound fallback
Reverse SSH tunnel

If overlay networking fails but general internet access works, the new machine can establish a reverse tunnel back to the controller.

Tier 4 · emergency local path
Same-LAN discovery
  • Printed IP on the console
  • mDNS announcement
  • Optional avahi support

Security rule: do not hardcode reusable Tailnet auth keys into the image.

Bootstrap authentication model

Treat the live image as semi-public media and keep the trust boundary temporary.

Recommended approach

  • Create a dedicated temporary bootstrap user
  • Authorize only controller-provided public keys
  • Disable password login
  • Rotate or discard temporary credentials after install
  • Do not reuse the everyday host user as the installer entry point

Avoid

  • Default passwords
  • Shared persistent private keys on installer media
  • Root SSH login unless there is a compelling reason

Remote agent workflow

Once reachable, the controller machine should do the adaptive work remotely.

1. Collect facts

Gather: lsblk, NVMe/SATA layout, removable devices, lspci, lsusb, dmidecode, ip link, firmware mode, secure boot state, RAM, CPU, GPU, and Wi-Fi chipset.

2. Pick an install strategy

Choose: known host profile vs new-host scaffold, laptop vs desktop defaults, and the disk layout policy.

3. Generate or update hardware-specific config

Derive on target: build hardware config from the new machine, copy facts back to the controller repo, and let the controller synthesize or review the host config.

4. Install remotely

Perform: partitioning, formatting, flake deployment, bootloader install, and system provisioning from the controller.

5. Cut over to normal Calnix access

Verify: the host comes back online under its real hostname using the permanent remote-access configuration.

Recommended implementation shape in this repo

Add a small live-image profile and keep the responsibilities separated into focused modules.

modules/bootstrap-connectivity.nix

  • DHCP / NetworkManager
  • Console status output
  • mDNS or local discovery helpers
  • Tailscale bootstrap support

modules/bootstrap-agent.nix

  • Wait for network
  • Report machine facts
  • Enroll into the remote-control path
  • Write status to logs and console

modules/bootstrap-ssh.nix

  • Temporary SSH hardening
  • Controller public-key injection
  • Dedicated temporary bootstrap user

Host/profile

hosts/bootstrap-image/configuration.nix should be a thin live-image profile that imports the bootstrap modules and avoids the full desktop stack.

Flake outputs

Add nixosConfigurations.bootstrap-image and/or a package output such as packages.x86_64-linux.bootstrap-iso.

nix build .#bootstrap-iso

Installation transport options

The simplest mental model is still controller-to-target SSH once the live environment is reachable.

Best likely path

Boot the live image, make it reachable over Tailscale or LAN SSH, then let the controller machine run the install remotely.

Tooling worth evaluating

  • nixos-anywhere for remote install orchestration
  • disko for declarative partitioning
  • nixos-facter for more structured hardware inventory

Console UX

A compact, high-signal boot screen can remove a surprising amount of setup friction.

Calnix Bootstrap ---------------- Ethernet: connected (192.168.1.44) Wi-Fi: not configured Tailnet: waiting for auth token SSH: bootstrap@192.168.1.44 Fingerprint: SHA256:... Next step: enter bootstrap token or connect via local LAN

What should be visible immediately

  • Temporary machine name or bootstrap ID
  • Ethernet and Wi-Fi state
  • Tailscale status
  • Reachable addresses
  • SSH fingerprint
  • Next local action if not connected
  • Short controller-side instructions

Security boundaries

The bootstrap image should be considered semi-public media.

No baked-in secrets

Use only short-lived or one-time enrollment material.

Minimal exposed surface

Do not expose extra services before authentication succeeds.

Clear audit trail

Record who connected and when during the bootstrap window.

Automatic cleanup

Discard temporary credentials after install or reboot.

If unattended flows come later, prefer age-encrypted controller metadata, signed bootstrap manifests, and limited Tailnet tags/ACLs.

Suggested phased roadmap

Build the smallest useful loop first, then add intelligence and polish.

Phase 1 · Minimal viable connectivity

Build: Ethernet DHCP, nmtui Wi-Fi, temporary SSH with injected controller key, optional Tailscale enrollment, and visible console status.

Success: boot a new machine, get it online, and SSH into it from the controller machine.

Phase 2 · Controller-driven install

Add: controller CLI helpers, fact collection, remote install orchestration or nixos-anywhere, and generated hardware-config copy-back.

Success: controller installs a reachable bootstrap machine end-to-end.

Phase 3 · Smart host selection

Add: hardware classification heuristics, host-template generation, disk-layout policy choice, and post-install validation.

Success: controller proposes the right configuration with minimal human input.

Phase 4 · Polished onboarding

Add: QR/file-based one-time enrollment, richer console UX, same-LAN discovery helpers, and optional remote progress UI.

Success: the setup path feels smooth without sacrificing the security model.

Key decisions still to make

These choices shape implementation order and complexity.

1. Primary reachability path: should Tailscale be the default, or only a fallback to LAN SSH?
2. Local onboarding UX: pure TUI now, or design for a tiny graphical flow later?
3. Install orchestration: adopt nixos-anywhere early, or keep phase 1 custom?
4. Disk layout policy: what should the controller assume on unknown hardware?
5. Automation boundary: should the controller generate a new host directory automatically, or only assist a human-reviewed flow?

Recommended next move

Keep the first slice narrow so connectivity can be validated in isolation.

  1. Create a bootstrap ISO profile in this flake.
  2. Give it Ethernet, Wi-Fi, temporary SSH, and optional Tailscale.
  3. Make the controller machine detect it and SSH into it.
  4. Only then layer on remote install automation.
